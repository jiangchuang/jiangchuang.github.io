达梦误删表（DROP TABLE）后的恢复 · 交互版

一条 DROP TABLE 敲下去，表和里面几百行数据一起消失。能不能救回来，取决于误删那一刻回收站是开还是关 —— 而达梦出厂默认是关。这篇把「开着的救法」和「关着的兜底」两条路都跑给你看。

单机实例实测 DM8 V8 2026-08-03 前提：RECYCLEBIN=1 9 步全程可复制
DROP TABLE FLASHBACK DBA_RECYCLEBIN dexp / dimp
定位说明：这是「快路」，不是标准做法。本篇讲的是回收站闪回，前提是 RECYCLEBIN = 1， 而达梦出厂默认是 0 —— 也就是说这条路径成不成立，在你 DROP 之前就已经定了。
有全库备份 + 连续归档时，标准做法是备份恢复（恢复到误删前时间点，再 dexp/dimp 导回）： 见 《达梦利用备份恢复误删表 · 交互版》。

步骤明细 已固定

左侧点一步，这里显示该步的完整命令与实测输出。点同一块可取消固定，按 Esc 也可取消。

一句话原理：FLASHBACK TABLE ... TO BEFORE DROP 不是"回滚 SQL"，而是把 DROP 时移进回收站（SYS.RECYCLEBIN$）的那份原始对象重新挂回用户命名空间。所以它救的是整张表，不能只挑几行；也不需要归档、不需要备份。

先查参数。这一步只要 3 秒，但决定了你是走闪回还是直接跳到第 8 步找备份。

-- 回收站开关：0=关（出厂默认），1=开
SELECT PARA_NAME, PARA_VALUE
  FROM V$DM_INI
 WHERE PARA_NAME = 'RECYCLEBIN';
实测输出（新建实例的出厂状态） 
LINEID  PARA_NAME   PARA_VALUE
1       RECYCLEBIN  0
返回 0 就意味着：这张表已经彻底没了，直接跳到第 8 步走备份恢复；返回 1 才继续第 2 步。
为什么不能现开现用：RECYCLEBIN 是静态参数，SP_SET_PARA_VALUE(1,...) 会直接报错： 
CALL SP_SET_PARA_VALUE(1,'RECYCLEBIN',1);
[-839]:Try to alter static ini parameter.
必须用 scope=2 写进配置文件、再重启实例才生效（见第 9 步）。而重启生效之后，之前 DROP 的表也不会回来。

在回收站视图里按原表名查。注意看 OBJECT_NAME 与 ORIGINAL_NAME 的区别：前者是它现在在系统里的真名（BIN$ 开头），后者只是"原来叫什么"。

-- 普通用户看自己的回收站
SELECT OBJECT_NAME, ORIGINAL_NAME, OPERATION, TYPE, DROPTIME
  FROM USER_RECYCLEBIN
 WHERE ORIGINAL_NAME = '<原表名>';

-- DBA 看全库（多一列 OWNER）
SELECT OWNER, OBJECT_NAME, ORIGINAL_NAME, OPERATION, TYPE, DROPTIME
  FROM DBA_RECYCLEBIN;
实测输出（DROP 一张带主键和普通索引的 ORDERS） 
OWNER      OBJECT_NAME      ORIGINAL_NAME    OPERATION  TYPE   DROPTIME
TEST_DROP  BIN$1029$0       ORDERS           DROP       TABLE  2026-10-26:21:30:29
TEST_DROP  BIN$134218804$0  CONS134218804    DROP       INDEX  2026-10-26:21:30:29
TEST_DROP  BIN$33555493$0   IDX_ORDERS_CUST  DROP       INDEX  2026-10-26:21:30:29
一张表会留下三行：表本身、主键背后的索引、自建索引。别看到三行就以为删了三张表。

用原表名闪回，不要用 BIN$ 那个名字。语句执行完，回收站里对应的行会同时消失。

FLASHBACK TABLE <模式名>.<原表名> TO BEFORE DROP;
实测输出 
SQL> FLASHBACK TABLE TEST_DROP.ORDERS TO BEFORE DROP;
executed successfully
used time: 14.307(ms)
14 毫秒，不需要停业务、不需要备份文件、不需要归档。
如果这里报 [-9805]：Recycle bin is disabled. —— 说明回收站本来就没开，这条路不存在，回到第 1 步的判断，转第 8 步。

闪回"成功"只代表对象挂回来了，不代表数据完整。三项一起看：行数、主键区间、业务汇总值。

SELECT COUNT(*) AS CNT, MIN(ID) AS MIN_ID, MAX(ID) AS MAX_ID, SUM(AMT) AS AMT
  FROM <模式名>.<表名>;

-- 闪回后回收站里对应的行应该已经没了
SELECT COUNT(*) FROM DBA_RECYCLEBIN WHERE ORIGINAL_NAME = '<表名>';
实测输出（DROP 前 200 行 / SUM=201000） 
CNT_RESTORED  MIN_ID  MAX_ID  AMT_RESTORED
200           1       200     201000

RECYCLEBIN_LEFT
0
行数、区间、汇总三项与 DROP 前完全一致，回收站对应条目已清空。

这一步几乎没人写在文档里，但它是真实事故里最容易翻车的地方。闪回之后，表和数据的名字回来了，索引名和约束名却还带着 BIN$ 前缀。

-- 先看现在是些什么名字
SELECT INDEX_NAME, INDEX_TYPE, STATUS FROM DBA_INDEXES
 WHERE TABLE_OWNER = '<模式名>' ORDER BY INDEX_NAME;
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE FROM DBA_CONSTRAINTS
 WHERE OWNER = '<模式名>';
实测输出（闪回之后，业务原来叫 IDX_ORDERS_CUST 和主键约束） 
INDEX_NAME       INDEX_TYPE  STATUS
BIN$33555496$0   NORMAL      VALID
INDEX33555494    CLUSTER     VALID
INDEX33555495    NORMAL      VALID

CONSTRAINT_NAME    CONSTRAINT_TYPE
BIN$134218805$0    P
数据是对的、索引也是 VALID，但名字全变了。业务代码里按名引用索引的地方会开始报错：DROP INDEX IDX_ORDERS_CUST、ALTER INDEX ... REBUILD、SQL hint 里写死索引名、按名比对的巡检脚本。 
-- 改回业务原名（注意 BIN$ 名要加双引号）
ALTER INDEX <模式名>."BIN$33555496$0" RENAME TO <原索引名>;
ALTER TABLE <模式名>.<表名> RENAME CONSTRAINT "BIN$134218805$0" TO <原约束名>;
实测输出（改名后） 
INDEX_NAME       INDEX_TYPE  STATUS
IDX_ORDERS_CUST  NORMAL      VALID
INDEX33555494    CLUSTER     VALID
INDEX33555495    NORMAL      VALID

CONSTRAINT_NAME  CONSTRAINT_TYPE
PK_ORDERS        P
两条语句都成功。改名前一定先查一遍实际名字，BIN$ 后面的对象号每次 DROP 都会变，直接抄别人的编号一定失败。

真实事故里很常见：DROP 完发现错了，情急之下先重建了一张同名空表，然后才想起来闪回。这时直接闪回会被同名对象挡住。

实测：直接闪回 
FLASHBACK TABLE TEST_DROP.ORDERS TO BEFORE DROP;
[-7041]:Database object [ORDERS] already exists.
-- 别删新建的那张表（那是二次事故），把回收到的那份落到旁边
FLASHBACK TABLE <模式名>.<表名> TO BEFORE DROP
  RENAME TO <新名_restored>;
实测输出 
FLASHBACK TABLE TEST_DROP.ORDERS TO BEFORE DROP RENAME TO ORDERS_RESTORED;
executed successfully

RESTORED_ROWS
200
NEW_TABLE_ROWS_STILL
1
老数据 200 行落到 ORDERS_RESTORED，后来新建的那张表 1 行没动。接下来慢慢比对、把数据搬回去，谁都不用再冒一次险。

下面三种情况，闪回这条路是真的走不通，别再耗时间试，直接转第 8 步或找物理备份。每条都有实测报错。

情况 实测报错 说明
回收站没开（出厂默认） [-9805] Recycle bin is disabled. DROP 时对象根本没进回收站，回收站里 0 行
DROP TABLE ... PURGE [-9807] Object is not in Recycle Bin. DROP 时主动跳过回收站，等于一步到位永久删除
TRUNCATE TABLE [-9807] Object is not in Recycle Bin. 表结构还在、数据清零，不进回收站，闪回救不了数据
反过来的好消息：实例重启不影响闪回。实测把一个 500 行的表 DROP 掉，直接 systemctl restart，重启后回收站里那 2 行还在（DROPTIME 没变），闪回照样成功、500 行一行不少： 
重启后 DBA_RECYCLEBIN：
TEST_DROP  T_REBOOT      2026-10-26:21:28:27
TEST_DROP  CONS134218801 2026-10-26:21:28:27

重启后闪回 → executed successfully
CNT_RESTORED  MIN_ID  MAX_ID
500           1       500
这和数据文件误删正好相反（那条路重启就彻底断掉）。所以 DROP 表之后不用慌到不敢重启，但也别去 PURGE 回收站。
两个清理回收站的坑（实测）
  1. PURGE TABLE <原表名> 会报 [-2106] Invalid table or view name [BIN$xxx]，什么也没清掉。想彻底删就用 DROP TABLE ... PURGE。
  2. PURGE RECYCLEBIN 只清当前用户自己的回收站。SYSDBA 执行时报"成功"，但另一个用户的表还在（实测前后都是 2 行）。要清别人的，得用那个用户连上去执行。

回收站没开、或者已经被 PURGE，就只能回到最后一次逻辑备份。这条路要求你之前导过；本篇实测用事先导出的单表 dmp 把整张表重灌回来。

# 日常就要有这一步：单表或整模式导出（FILE 用全路径）
dexp SYSDBA/<密码>@localhost:5236 \
  FILE=/home/dmdba/bak/orders_backup.dmp \
  LOG=/home/dmdba/bak/dexp_orders.log \
  TABLES=<模式名>.<表名>

# 误删之后：把表导回来
dimp SYSDBA/<密码>@localhost:5236 \
  FILE=/home/dmdba/bak/orders_backup.dmp \
  LOG=/home/dmdba/bak/dimp_orders.log \
  TABLES=<模式名>.<表名> IGNORE=Y
实测输出（导出 → DROP 掉 → dimp 灌回） 
dexp: table ORDERS_RESTORED export terminate, total export 200 rows, size 3.785 KB

dimp: [1/2]create table ORDERS_RESTORED
dimp: import table ORDERS_RESTORED , has coped with 200 rows, size 3.785 KB
dimp: [2/2]import successfully...

CNT_AFTER_DIMP  MIN_ID  MAX_ID  SUM_AMT
200             1       200     201000
行数、主键区间、汇总值与 DROP 前完全一致。
dexp 的两个坑（实测踩到）
  1. FILE= 必须写全路径。如果写成 FILE=xxx.dmp DIRECTORY=/某个目录，命令会静默退出、不产出文件、连日志都不写 —— 看起来"跑了"其实什么都没做。
  2. TABLES= 要写 模式名.表名，只写表名可能导不到东西。

这篇指南最大的价值不在抢救，而在于提前把抢救的前提配好。三件事，配置一次，长期受益。

-- 1) 打开回收站（静态参数：scope=2 写配置文件，重启生效）
CALL SP_SET_PARA_VALUE(2,'RECYCLEBIN',1);
-- 重启实例后确认
SELECT PARA_NAME, PARA_VALUE FROM V$DM_INI WHERE PARA_NAME='RECYCLEBIN';

-- 2) 看回收站占用与保留策略（按需调，别让它无限涨）
SELECT PARA_NAME, PARA_VALUE FROM V$DM_INI
 WHERE PARA_NAME IN ('RECYCLEBIN','RECYCLEBIN_RETENTION','RECYCLE');

-- 3) 定期盘点回收站，确认没有"以为删了其实还占着空间"的对象
SELECT OWNER, ORIGINAL_NAME, DROPTIME FROM DBA_RECYCLEBIN ORDER BY DROPTIME;
实测参数（本版默认值） 
PARA_NAME             PARA_VALUE
RECYCLE                300
RECYCLE_POOLS          6
ENABLE_FLASHBACK       0
UNDO_RETENTION         90.000000
RECYCLEBIN             0
RECYCLEBIN_RETENTION   0
RECYCLEBIN=0 是这篇指南存在的原因。ENABLE_FLASHBACK=0 是另一个开关（管的是"闪回查询/闪回版本"，能看历史行、不能救 DROP 表），别和回收站混为一谈。
还要配的两件事：
  1. 逻辑备份：至少对核心业务表做每日 dexp，保留 7 天以上。这是回收站之外的唯一低成本兜底。
  2. 归档 + 全量备份：TRUNCATE 和 PURGE 之后唯一的路就是时间点恢复，前提是归档开着。没开归档的库，这两类事故等于直接判死刑。

常见问题

都是这轮实测里真碰到的疑问。

是这条路没救了，不是这个库没救。[-9805] 的含义是"回收站是关闭的"，也就是说 DROP 的那一刻对象就没进回收站，系统里连残骸都没有。任何版本的闪回语法都变不出来。

正确动作：立刻停止在库上做任何 DDL，转向（1）找最近一次 dexp 备份做 dimp 恢复；（2）如果有归档+全备，做时间点恢复；（3）从业务侧（上游系统、日志、报表库）重建数据。

不能。回收站是静态参数，scope=1 直接报 [-839] Try to alter static ini parameter，必须 scope=2 写配置文件再重启实例。而重启生效之后，参数只对之后发生的 DROP 生效 —— 之前 DROP 的对象从来没有被记录过，无从恢复。

所以这个参数的正确态度是：现在就开，为了下一次。

都不能。FLASHBACK TABLE ... TO BEFORE DROP 恢复的是整个对象，状态就是 DROP 那一刻的状态，没有部分恢复、也没有时间点参数。

如果你要的是"看某一行在半小时前是什么值"，那是闪回查询（FLASHBACK QUERY / VERSIONS），由 ENABLE_FLASHBACK 和 UNDO_RETENTION 控制，和回收站是两套机制，本篇不涉及。

会占空间。DROP 进回收站的对象仍然占用它原来的表空间，只是名字变成 BIN$ 开头的、用户看不见。所以"我删了表，空间怎么没降"是正常现象。

本版相关参数：RECYCLEBIN_RETENTION（保留策略）、RECYCLE=300、RECYCLE_POOLS=6。实践上建议定期 SELECT ... FROM DBA_RECYCLEBIN ORDER BY DROPTIME 盘点，确认没有长期滞留的对象，再按需 DROP TABLE ... PURGE 或按用户 PURGE RECYCLEBIN。

不能直接照抄。本篇所有输出取自单机实例（DM01，192.168.31.14:5236）。集群环境下回收站参数、视图可见范围、以及 FLASHBACK 语句该在哪一类节点上执行，都需要单独实测确认。

按以往经验，DPC 里实例级参数的查询要落到 MP 上做（BP 节点查部分 DPC_* 视图会报 [-3818]）。这块等实测完再单独出一篇，不要在集群上按单机的直觉操作。

本篇没有实测 DROP USER ... CASCADE 的闪回，不要假设它和 DROP TABLE 一样。回收站记录的是"对象被 DROP"，用户被级联删除时对象是否入回收站、闪回后权限与默认表空间能否一并恢复，都需要单独验证。

保守做法：整用户被删 = 按"整库级事故"处理，走向备份 / 时间点恢复，别单独试闪回。
