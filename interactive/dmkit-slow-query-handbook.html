!使用前必读 · 三条边界

1 · 采集分两个档位，默认是「不执行 SQL」的那一档

档位命令会不会执行你的 SQL拿到什么少了什么
只读档（默认）at --file slow.sql不执行执行计划、涉及表、关键列索引、索引建议实测耗时、逻辑读、真实扫描行数
完整档at --file slow.sql --run执行一遍上面全部 + 实测耗时/逻辑读/物理读无，但会付出真实耗时

先在只读档跑，觉得信息不够再决定要不要 --run。只读档对生产库是安全的——它只让优化器给个计划（EXPLAIN），不取数据、不锁行、不触发函数副作用。

qopt 同理：不带 --run 就是只读档，--run / --with-10053 才执行。ix 会逐条执行，属于完整档。

完整档会真实执行，跑之前先确认业务上能接受这段时间。这四类语句尤其要小心：大表全扫、SELECT ... FOR UPDATE（持锁）、含自定义函数（可能有副作用）、跨表 JOIN 大结果集。

2 · 工具的建议是参考，不是结论

索引建议按「全表扫描行数阈值」这类启发式规则给出，不理解业务语义。CREATE INDEX 语句只打印、不执行，落库前请人工判断：这个索引会不会影响写入性能、是否与既有索引重复。

3 · 视图名可能随版本变化

本手册的命令在 DM8 上验证。不同小版本的动态视图列名可能有差异，遇到「表或视图不存在」时，以本机实际视图为准：

SELECT VIEW_NAME FROM ALL_VIEWS WHERE VIEW_NAME LIKE 'V$SQL%' ORDER BY 1;

⚡两分钟版 · 赶时间只看这一块

准备：解压到 C:\dmkit，在该目录打开 PowerShell，把慢 SQL 存成 slow.sql（UTF-8）。

验证工具能跑

表不在当前模式（报 -2106 Invalid table or view name）？在端口后面带 ?schema=模式名

看完觉得「还想要实测耗时 / 逻辑读」，再加 --run（会真实执行一遍）

把 at_report.md 发出去时，附上下面的说明

三条铁律 · 不遵守会白忙

1
SQL 一律走 --file，别写在命令行里视图名里的 $ 会被 PowerShell 当变量吃掉，报错还看不出原因
2
DSN 用单引号包住 'dm://...'PowerShell 双引号会展开 $；cmd 里反过来要用双引号
3
尽量要一个 DBA 只读账号普通账号查 V$SQL_HISTORY 会直接报 -5504 无权限——那不是 SQL 写错，是权限不够（见 §2.4）

两个报错，一眼分清 · 别在这耗时间

报错真实原因怎么改
-2106 Invalid table or view name表在别的模式、SQL 没写前缀；或视图名写错端口后带 ?schema=模式名；或 SQL 里写全 模式名.表名
-5504 No select privilege账号没权限换 DBA 账号，或让 DBA 授权（§2.4）

?schema= 只能写在 --dsn 里，at 没有 --schema 参数（q 才有）。写成 at --schema 会报「没有 --schema 这个参数」。

0先明确：为什么需要这个手册

慢查询定位不了，通常不是技术不够，是信息不够。

你手上有的别人能判断出
「有个查询很慢」什么也判断不了
「这条 SQL 很慢」能猜，但猜不准
SQL 全文 + 执行计划 + 实测指标 + 表规模能指出瓶颈在第几步、该改什么

所以这份手册唯一的目标：用最低的操作成本，把这四样凑齐。

注意「表有多大」常被忽略，但它直接决定该不该建索引——同样的 SQL，1 万行全扫是正常的，1 亿行全扫就是灾难。

2连上数据库 · 关键一步

2.1 先凑齐 4 个信息

项举例从哪来
主机 IP192.0.2.10由 DBA 或运维提供
端口5236（达梦默认）同上
账号SYSDBA同上
密码——同上

本机安装的库，IP 填 127.0.0.1 即可。

2.2 一条命令验证连通

dmkit q --ping --dsn 'dm://SYSDBA@192.0.2.10:5236'
  • DSN 用单引号包起来——PowerShell 里必须这样（双引号会展开 $）。
  • 不写密码。回车后提示输入，屏幕不显示字符——这是故意的，不是卡住。好处：密码不进命令历史，也不会被 ps 看到。
  • 用 cmd（黑窗口） 的话，cmd 不认单引号，要改成双引号；cmd 里 $ 没有特殊含义。
分辨终端提示符以 PS C:\> 开头 = PowerShell；以 C:\> 开头 = cmd。图省事就用 PowerShell，本手册全部按 PowerShell 写。

密码确实要写进命令时（比如脚本），整个 DSN 用单引号包住：

dmkit q --ping --dsn 'dm://SYSDBA:你的密码@192.0.2.10:5236'
密码特殊字符 含 @ 不用转义（驱动按最后一个 @ 切分账号和主机）； 含 ? 要在 DSN 末尾再补一个 ?，否则报 9001； 不要用 %40 这类 URL 编码——驱动不解码，会当成密码的字面字符，直接认证失败。
脚本场景「省略密码」只在交互终端有效。批处理脚本或用管道跑（dmkit ... | tee log.txt）时会被拒绝并明确提示——这时把密码写进 DSN，或加 --password-stdin。

2.3 连不上怎么办

--ping 会分四层告诉你卡在哪，照着它给的结论走：

卡在含义你该做什么
DNS主机名解析不了把主机名换成 IP 试
TCP端口不通查防火墙、实例是否在跑、端口对不对
握手 / 认证端口通但连不上 / 账号密码错端口通 = 网络没问题，问题在实例或口令
查询连上了但查询失败权限问题或库状态异常
边界端口通 ≠ 能连库。「telnet 通但库连不上」极常见（实例挂了、监听异常、认证失败），必须用 --ping 判断，不能用 telnet。

2.4 账号权限：决定你能采到多少

账号类型能采到什么影响
DBA 类（SYSDBA 或带 DBA 角色）全量：逻辑读、物理读、服务端耗时、10053 trace推荐
普通账号降级：只有客户端耗时 + 预估计划少掉「真实疼在哪」的关键证据

dmkit 遇到普通账号会自动降级并如实提示，不会假装采到了。

建议使用一个「有 DBA 角色的只读账号」——既能采全，又不担心误操作。

普通账号到底能查什么（DM8 默认配置实测，仅 RESOURCE 角色）：

视图普通账号
V$INSTANCE、V$VERSION、V$DATABASE✅ 可查（默认对 PUBLIC 开放）
USER_TABLES、ALL_TABLES✅ 可查（只含自己有权限的）
V$SESSIONS、V$SQL_HISTORY、V$SQL_STAT、V$SQL_PLAN、V$TRXWAIT、V$LOCK、V$DM_INI❌ -5504
DBA_TABLES、DBA_USERS、DBA_INDEXES、DBA_SEGMENTS、DBA_DATA_FILES❌ -5504

也就是说：慢查询采集靠的视图，普通账号一个都查不到。报 -5504 不是 SQL 写错，加 SET SCHEMA 也没用——那是权限，不是模式。

确实只能用业务账号时，让 DBA 执行这一条（实测可覆盖上述全部视图，不必给 DBA 角色）：

GRANT SELECT ANY DICTIONARY TO 你的账号名;

用完想收回：

REVOKE SELECT ANY DICTIONARY FROM 你的账号名;
-- 撤完核对一眼，确认真的没了
SELECT GRANTEE, PRIVILEGE FROM DBA_SYS_PRIVS WHERE GRANTEE='你的账号名';
注意授权 / 撤销后要重新连接才生效，已有连接仍是旧权限。

表不在当前模式是另一种报错：-2106 Invalid table or view name，跟权限无关——表确实存在，只是不在登录用户的默认模式里。两种修法：SQL 里写全 模式名.表名，或在 --dsn 端口后加 ?schema=模式名（at 只能走后者，它没有 --schema 参数）。

3找到那条慢 SQL

3.1 情况 A：你已经知道是哪条

从这些地方拿：应用日志里的慢 SQL 记录 / 达梦管理工具的会话或历史 SQL / 使用者描述的「点这个按钮就卡」对应到的那条查询。

  • ✅ 完整原文，从头到尾，包含所有 WHERE 条件
  • ❌ 不要只截图（别人没法复制复现，也容易被截断）
  • ❌ 不要只给前 1000 字符（TOP_SQL_TEXT 会截断，看不全就判断不了谓词写法）

3.2 情况 B：不知道是哪条，只知道「库慢」

把它存成 find_top20.sql：

SELECT SQL_ID, TIME_USED, N_LOGIC_READ, SUBSTR(TOP_SQL_TEXT,1,80) AS SQL_HEAD
  FROM V$SQL_HISTORY
 ORDER BY TIME_USED DESC
 LIMIT 20;
dmkit q --dsn 'dm://SYSDBA@192.0.2.10:5236' --file find_top20.sql

按 TIME_USED（总耗时）和 N_LOGIC_READ（逻辑读）排序，两个都高的那条最值得查。

实测更正 DM8 真机验证过的三处反直觉：
· V$SQL_HISTORY 里没有 SQL_TEXT_ID 列，跨视图关联键是数字 SQL_ID
· V$SQL_STAT 只保留当前缓存里的少量 SQL（实测只有 4 行），查历史慢 SQL 必须用 V$SQL_HISTORY
· 会话视图是 V$SESSIONS（复数），V$SESSION 不存在

想看 SQL 全文（绕开 1000 字符截断）：

SELECT SQL_ID, SQL_TEXT FROM V$SQLTEXT WHERE SQL_ID = '上一步的ID';

3.3 把 SQL 存成文件（★ 这一节能救你 90% 的报错）

为什么必须这么做：SQL 直接写在命令行里，会被终端「吃掉」字符，而且报错信息完全看不出原因。

你在 PowerShell 里敲的实际传给 dmkit 的结果
--sql 'SELECT 1 FROM V$SQL_HISTORY'SELECT 1 FROM V$SQL_HISTORY✅ 正确
--sql "SELECT 1 FROM V$SQL_HISTORY"SELECT 1 FROM V❌ $SQL_HISTORY 被当成变量，替换成空

V$SQL_HISTORY、V$SESSIONS、STATUS$ 这些名字全都有 $，用双引号包等于自毁。而这时的报错通常表现为「表或视图不存在」——你会去怀疑库，实际是命令打错了。

另外几个报错来源：SQL 里的字符串 'CODE500' 和单引号冲突、& % ^ 被 shell 解释、换行丢失。

解法把 SQL 存成文件，用 --file。文件里写什么，dmkit 就收到什么，跨 Windows / Linux / cmd / PowerShell 全都不出问题。
  1. 用记事本或 VS Code 新建文件，存成 slow.sql
  2. 把 SQL 原文原样粘进去，末尾加分号 ;
  3. 保存时编码选 UTF-8
  4. 命令里写 --file slow.sql

4采集 · 三种深度，按需要选

别一上来就用最重的。先看这张决策表：

深度命令是否执行 SQL耗时什么时候用
快档 · 只读dmkit at否几秒默认选这个，判瓶颈 80% 够用
快档 · 完整dmkit at --run是几十秒起需要「有多疼」的量化证据
全档dmkit qopt加 --run 才是几分钟快档看不出原因 / 要交给专家深挖

4.1 快档：一屏拍照（★ 首选）

先跑默认的只读档：

dmkit at --dsn 'dm://SYSDBA@192.0.2.10:5236' --file slow.sql --out at_report.md

看完觉得还缺「到底有多疼」的量化证据，再补一次完整档：

dmkit at --dsn 'dm://SYSDBA@192.0.2.10:5236' --file slow.sql --run --out at_report.md

两档的差别只有一块——实测指标：

块只读档完整档
① 精简后的 SQL✓✓
② 实测指标（耗时/逻辑读/物理读）✗ 拿不到✓
③ 关键计划行✓✓
④ 涉及表与关键列索引✓✓
⑤ 索引建议（可执行的 CREATE INDEX）✓✓
一句话判「瓶颈在第几步」用只读档就够；要「改完快了多少」的对比数据，才需要完整档。

只读档真实输出（5 万行表、CODE 无索引、WHERE CODE='CODE500'）：

◆ 实测（⊘ 只读档 · 未执行原 SQL）
  无实测耗时/逻辑读/真实扫描行数——这些只有真跑一次才有。
  计划、涉及表、索引建议照常可用，判瓶颈通常够用。
  要真实指标：在命令末尾加 --run（原句执行一遍，慢 SQL 会花掉它真实的耗时）

◆ 计划（EXPLAIN FOR，关键行）
  4 #CSCN2 T_RO_TEST(INDEX33555503)  [全扫] 预估50,000

◆ 涉及表与关键列索引
  T_RO_TEST（行数未知：未收集统计；dmkit stat --table T_RO_TEST 可补）
    CODE     VARCHAR        无索引 ←

◆ 索引建议（依据自行取舍；批量复核用 dmkit ix）
  ✗ T_RO_TEST(CODE)  ←  预估全表扫描 50,000 行（ROW_NUMS）
  CREATE INDEX IDX_T_RO_TEST_CODE ON "SYSDBA"."T_RO_TEST" ("CODE");

完整档多出来的那一行：

◆ 实测（真实执行）
  耗时 6ms ｜ 逻辑读 72 ｜ 物理读 0 ｜ 返回 1 行 ｜ SQL_ID 219
怎么看这一屏 CSCN2 = 全表扫描，SSEK2 = 走了索引。CSCN2 + 行数很大，就是索引问题。
[全扫] 却写「索引建议：无」时，看下面那两行解释——最常见是谓词套了函数（SUBSTR(col,1,4)=...、NVL(...)、col+1），普通索引天然用不上，要改写谓词或建函数索引。这种情况工具不会瞎给 CREATE INDEX。
「行数未知」表示这张表还没收集统计信息，不代表表是空的。
参数默认说明
--read-only默认即为它显式指定只读档（与 --run 互斥）
--run关完整档：真实执行一次，多出实测指标
--min-rows10000全扫行数低于此值不提示建索引（小表全扫正常，避免乱建议）
--max-rows20客户端最多取回行数，只影响计数展示，不影响执行
--timeout120真实执行超时秒数（只读档不涉及）
不写档位会怎样在终端里手敲会问你一次（回车 = 只读，选 2 才执行）；写成脚本或用管道跑则一律走只读，不会静默执行。
只打印不执行建议的 CREATE INDEX 只打印，落库前请人工判断。

4.2 全档：完整现场报告

dmkit qopt --dsn 'dm://SYSDBA@192.0.2.10:5236' --file slow.sql --with-10053 --out report.md
段内容解决什么问题
1实例与环境：版本、页大小、字符集、大小写敏感别人本地复现必须对齐，否则计划不可比
2优化器参数（非默认值会标 ⚠️）该环境的个性化配置常是计划异常的元凶
3预估执行计划优化器「以为」会怎么跑（不执行语句）
4对象 DDL + 表/列注释表结构、字段含义
5统计信息：行数/NDV/NULL/直方图/收集时间 + 索引判断「估算为什么错」
6真实执行：预估 vs 实际行数 + 各算子耗时定位最贵的那一步
710053 判读（说人话）优化器为什么选了这个计划
8本地复现指引专家在自己机器上重建现场
# 最完整（真实执行 + 优化器决策跟踪）
dmkit qopt --dsn ... --file slow.sql --with-10053 --verify-ndv --out report.md

# 只采集不执行（大表不敢跑时用；这就是不写 --run 的默认行为）
dmkit qopt --dsn ... --file slow.sql --out report.md

# 拿到 .trc 文件，离线判读（不连库）
dmkit qopt --trace-file example.trc
代价--run 和 --with-10053 会真实执行目标 SQL，大表注意代价。不加时零副作用（EXPLAIN 只走优化器，不产生结果集）。
先建目录对象--with-10053 需要 DBA 权限，且依赖一个 UTL_FILE 目录对象 PLN_TRC：首次使用要先跑一次 dmkit qopt --setup-dir ... 把它建出来（这是库级写操作）。不先建的话，--with-10053 只会告警、跳过这一段，不会偷偷替你建。

4.3 进阶档：批量查漏建索引

dmkit ix --dsn 'dm://SYSDBA@192.0.2.10:5236' --file top_list.txt --yes
格式要求dmkit ix 的输入是 dmsqlq -o 导出的清单格式，不是随便一个普通 .sql 文件。手上只有普通 SQL 文件时，先确认格式能不能被识别。
会逐条真跑清单里如果有 UPDATE/DELETE，先剔掉。生成的 DDL 不要盲跑，逐条核对后再建。

4.4 发出前自检 · 4 问

  • SQL 是完整的吗？有没有被截断、有没有省略号
  • 有执行计划吗？哪怕只是 CSCN2 一行也算
  • 有量化指标吗？逻辑读 / 耗时，光说「很慢」没用
  • 表有多大？几万行还是几亿行，结论完全不同

采集方式怎么发

at --out at_report.md上传 .md 文件，或粘内容

5.2 附带说明（复制这段，把括号填掉）

【背景】达梦 DM8，业务系统（什么业务） 【现象】这条 SQL 平时（X 秒），现在（Y 秒）；（一直慢 / 最近突然变慢） 【表规模】（约多少万 / 亿行） 【已尝试】（没试过就写「没试过」） 【想要】请判断瓶颈在第几步，给出可执行的优化动作，并说明改完预期能快多少 【附件】上面是 dmkit 采集的执行计划与实测指标
最关键的一句「一直慢 / 突然变慢」——一直慢多半是设计问题（缺索引、谓词写法），突然变慢多半是数据量涨了、统计信息过期、或锁。方向完全不同。

5.3 发之前：建议处理掉这些

  • 表名/字段名 → 可保留（不影响判断），如涉及敏感信息就换成 T1/T2、C1/C2
  • 具体数据值（身份证、手机号、金额）→ 替换或删掉
  • IP、主机名、实例名 → 建议替换
  • 账号密码 → 永远不要发

附判断慢查询的五个方向 · 速记

拿到执行计划后按这个顺序看：先改天花板，再看放大系数，最后才怀疑统计。

序计划里的信号说明动作
①CSCN2 全表扫 + 行数巨大没索引，在读全表建索引
②有索引但仍 CSCN2谓词写法让索引用不上（列上函数 / 隐式转换 / LIKE '%x'）改写谓词
③NL 方向反 / 多余物化驱动表选错调连接顺序 / 换 HASH
④预估行数 vs 实际差一个数量级统计信息过期收统计（先验证逻辑读是否真降）
⑤计划正常但仍慢锁等待 / 高水位 / 资源竞争查锁、查资源

两条实测铁律 · 省你两天

铁律 1收统计不是万能药。实测某慢查询从「无统计」收到「精确」：耗时 5921 → 5894 ms（-0.5%），逻辑读 15,596,271 一点没变。收统计只解决「估算错」，不解决「该读的数据本来就多」。
铁律 2谓词改写才是大头。同一案例，LIKE CONCAT(前缀,'%') → SUBSTR(CODE,1,4)=前缀：耗时 5921 → 462 ms（-92%），逻辑读 -98.7%。「读多少」由谓词决定，「怎么读」由索引决定——先改谓词，再谈索引。
