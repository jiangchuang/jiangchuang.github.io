把 ? 换成真实值，写成能直接执行的 .sql：

dmsqlq D:\dmsql_log -o out.sql
out.sql 里长这样： 
-- 2026-09-10 09:00:00 · [SEL] · 0.1ms · SYSDBA, · trxid:3816438, · SAMPLE
SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000000' AND status = 0;

-- 2026-09-10 09:00:00 · [UPD] · 0.5ms · SYSDBA, · trxid:3816438, · SAMPLE · /*未找到匹配参数: 占位符2个*/
update ACCOUNTS set BALANCE = BALANCE + ? where ACCT_ID = ?;
两条对照看就懂了：第一条参数填好了，第二条工具明说了「没找到参数」而不是假装还原成功 —— 这类行多半是采集侧没记下 PARAMS（见问题区）。

只想看超过 1 秒的、按耗时倒序取最慢 20 条：

dmsqlq D:\dmsql_log -m 1000 -B 20 -o slow.sql
实际输出（样例取最慢 3 条）： 
-- 2026-09-10 09:09:59 · [SEL] · 60ms · SYSDBA, · trxid:3816637, · SAMPLE
SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000599' AND status = 5;

-- 2026-09-10 09:09:58 · [SEL] · 59.9ms · SYSDBA, · trxid:3816637, · SAMPLE
SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000198' AND status = 0;

常见问题：只有卡住了才需要往下看

大概率是没采集到，不是没发生。工具会直接把这件事挑明：

  采集缺口   缺位号 29：本批日志无事务/锁事件行（TRX: / DLCK / LOCK_TID 全为 0）
             → 「锁等待」「长事务」「TPS」是没采集到，不是没发生

判据很硬：29 位号一旦开启，事务事件行必然大量出现，不可能恰好是 0。 要这一维度就在 sqllog.ini 的 SQL_TRACE_MASK 里打开 29 重采； 短期替代是在库上查 V$TRXWAIT / V$LOCK。

工具还会顺手做一份采集配置体检：缺 28 就没有参数行，缺 27 就没有原始语句，缺 23 就没有报错语句 —— 这类「查不出来」的问题，第一嫌疑永远是采集侧配置，不是解析器。

因为「没还原」和「还原错了」是两种完全不同的后果：前者你知道要手工补，后者你会拿着一条假 SQL 去复现一个不存在的现场。 所以工具把还原不出来的语句原样保留 ?，并在注释头里写明占位符个数，绝不静默编一个值进去。

常见原因：这条语句执行前日志里根本没有对应的 PARAMS 行（采集侧没记，位号 28）； 或者是日志被截断、跨文件的会话块不匹配。

贴什么最有帮助

① 完整报错或异常输出（含工具提示的「采集缺口」行）；
② 你执行的那条命令原文；
③ dmsqlq --version 的输出与操作系统 —— 版本不同，行为可能不同。

不要贴什么

生产库的真实日志全文、客户表结构、连接串与口令。定位问题不需要这些 —— 先用 -m / -B 把范围卡小。
