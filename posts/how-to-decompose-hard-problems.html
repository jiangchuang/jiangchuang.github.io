把「难」拆开：四种难，四种解法

工作方法

有件事你拖了三天。每天打开电脑都想着它，但每次都没真正开始——不是不想做，是不知道从哪下手。

这时候人的本能是列一张 TODO：拆成十条，排在待办里，然后看着那张表更焦虑了。

先说清楚：这篇不涉及达梦的具体技术。它讲的是「遇到难事怎么下手」，只是案例全部来自达梦现场的活。

一、先纠一个误解：拆解不是切分

大多数人以为「难」等于「活多」，所以第一反应是切分任务。但切分只对一种难有效——路径清楚、纯粹量大的那种。

而真正的难，多半是另外三种：

  • 说不清「做完是什么样」
  • 不知道该查什么、该信谁
  • 知道要什么，但不知道下一步做什么

这三种，切得再细也没用——因为你切出来的每一块，都还是「不知道下一步」。

核心判据：难的本质不是「事大」，是「你不知道下一步做什么」。
所以拆解的目标不是变小，是变确定。

二、先诊断：难有四种

类型症状第一动作
① 定义不清说不清「做完是什么样」写验收标准，不写方案
② 信息不足不知道该查什么、该信谁找最小权威源
③ 路径不明知道要什么，不知道怎么走做最小可证伪实验
④ 量太大路径清楚，纯粹活多这才是切分

我在自己的活里粗算过：前三种占绝大多数，第四种很少。但人的本能是往第四种上靠——因为列清单最省脑子，看起来也最努力。

最常见的误判：把 ①②③ 当成 ④，然后列一张 TODO。那是用「看起来很努力」掩盖「还没想清楚」。

三、四种解法

① 定义不清 → 先写「做完的样子」

不是写方案，是写验收条件。差别有多大：

反例正例
做个同步工具两个进程同时取号，拿到不同号且都退出 0
优化一下性能同一 SQL 从 3.2 秒降到 500 毫秒以内，且执行计划里没有全表扫描

验收标准一写出来，方案往往就唯一了。定义问题的过程本身就在解题——这也是为什么很多人「一想清楚就知道怎么做了」，不是灵光乍现，是定义到了位。

② 信息不足 → 找「最小权威源」

不要一上来读全手册。按命中率排序找三样东西：

  1. 踩过坑的人 / 自己的小本本——成本最低、命中率最高
  2. 权威文档的相关那一节（不是整本）
  3. 一个能跑的最小例子

判据是：你需要的是一条能落地的答案，不是一次系统学习。系统学习是另一件事，别拿它当借口拖延开始。

③ 路径不明 → 做「最小可证伪实验」

不是做原型，是做一个能推翻你假设的实验。

举个我自己的例子：要在 Windows 沙箱里装一个达梦库做全自动视频测试，红线是绝不能碰宿主机。整件事最不确定的只有一个点——沙箱能不能接受命令行传进去的配置文件。

所以我没先去写整套自动化，而是只测这一件：传配置文件启动 → 秒退，返回 -2147024713。结论立刻明确：无头传参这条路不通，改走图形界面双击。一次实验，省掉了后面所有弯路。

设计实验先问三句：

  • 这个实验要是失败了，我会因此改变方案吗？（不会 → 别做）
  • 它要多久？（超过半小时 → 拆得更小）
  • 结论怎么记？（不记等于没做）

④ 量太大 → 才切分，按依赖顺序

不是按重要性，是按「谁必须先完成」。

重要性排序会让你先做最容易出彩的那块，最后卡在最难的那块——而最难的那块才是决定成败的。按依赖顺序排，最难的通常被推到最前面，因为后面全等它。

四、一条前置原则：先做「如果不成，全盘皆输」的那一步

难事之所以耗时间，往往不是因为工作量大，而是中途发现方向错了，全盘重来。

所以拆解时先问一句：哪一步失败会让整个方案作废？把它放到最前面。

另一个例子：给一个协作脚本做「并发取号不重复」。整件事最可能推翻全局的假设是——git 的推送校验到底能不能保证并发原子性。如果它不能，整个设计就得换。

所以我没有先写工具，而是先起两个进程同时跑。第一轮就挂了：一个进程推送被拒后，卡在 rebase 冲突里，拿不到号。五分钟发现一个会推翻设计的 bug，比写完三百行再发现划算得多。

判据：把验证成本最低、推翻力最强的那个假设，排到第一位。

五、什么时候该放弃

这条最难，但最省钱。判据不是时间，是信息增量：

  • 每次失败都能说出「下次不这么干，因为 X」→ 继续
  • 连续两次失败只是重复同一个错误、没拿到新信息 → 换路

耗了三小时但每次学到东西，值得；耗了二十分钟但原地打转，该停。时间不是判据，「学会了什么」才是。

六、五分钟版

真到现场，就按这个顺序问自己四句：

1. 做完是什么样？        —— 说不清 → 定义问题（写验收标准）
2. 该查什么、信谁？      —— 不知道 → 信息问题（找最小权威源）
3. 下一步做什么？        —— 不确定 → 路径问题（做最小可证伪实验）
4. 只是活多？            —— 是     → 才切分（按依赖顺序）

四句里只要有一句答不上来，就还没到「切分」这一步。

七、常见问题

Q1：四种难同时占怎么办？

按顺序解：定义 → 信息 → 路径 → 量。定义不清时，后面三种的答案都是假的——你会为一个还没定义清楚的问题做实验。

Q2：拆到什么粒度算够？

拆到每一块都能立刻动手为止。如果某一块你看着还是「不知道从哪开始」，说明它没拆完，或者它根本不是量的问题。

Q3：最小可证伪实验和「做个原型」有什么区别？

原型是为了证明能做，实验是为了证伪假设。原型会越做越大（因为你想让它能跑），实验做完就该扔。判断标准：这个实验失败了，我会不会改方案？会，才算实验。

Q4：怎么记录实验结论才不算白做？

四件套：环境、命令、原始输出、结论。少一样，三个月后你自己都不认。这条和排查问题记日志是一个道理。

Q5：这套方法对「必须做完但真的很无聊」的事有用吗？

没用。那种事不需要拆解，需要的是定时器和外部约束。别把方法论套在意志力问题上。

这篇是 v1。几种难的占比是经验估计、没有统计；「实验超过半小时就再拆小」的阈值是拍脑袋定的。你按这个试几次，哪条不成立就回来告诉我，我改。
