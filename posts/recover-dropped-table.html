达梦误删表（DROP TABLE）后的恢复

故障恢复

📋 想照着做？这篇有 交互操作版——左侧步骤卡片导航、命令一键复制，现场照着敲更方便：打开交互操作版 →

本文内容与交互版逐条对应，命令均为实测输出，未做删改。占位符 <…> 请按本机环境替换后执行。

先看结论：两条路，一条几秒钟，一条几十分钟

DROP TABLE 之后有两条路：回收站闪回（回收站开着的话，几秒钟，不需停业务、不需备份）和备份时间点恢复（兜底方案，要建恢复库、跑归档）。先查回收站开关，再决定走哪条。

九步速成：把误删的表救回来

第 1 步：先确认回收站开没开

-- 回收站开关：0=关（出厂默认），1=开
SELECT PARA_NAME, PARA_VALUE
  FROM V$DM_INI
 WHERE PARA_NAME = 'RECYCLEBIN';

实测输出（新建实例的出厂状态）：RECYCLEBIN = 0。返回 0 就意味着：这张表已经彻底没了，直接跳到第 8 步走备份恢复；返回 1 才继续第 2 步。

为什么不能现开现用：RECYCLEBIN 是静态参数，SP_SET_PARA_VALUE(1,...) 会直接报错：[-839]:Try to alter static ini parameter. 必须用 scope=2 写进配置文件、再重启实例才生效（见第 9 步）。而重启生效之后，之前 DROP 的表也不会回来。

第 2 步：在回收站里找到被删的表

-- 普通用户看自己的回收站
SELECT OBJECT_NAME, ORIGINAL_NAME, OPERATION, TYPE, DROPTIME
  FROM USER_RECYCLEBIN
 WHERE ORIGINAL_NAME = '<原表名>';

-- DBA 看全库（多一列 OWNER）
SELECT OWNER, OBJECT_NAME, ORIGINAL_NAME, OPERATION, TYPE, DROPTIME
  FROM DBA_RECYCLEBIN;

实测输出（DROP 一张带主键和普通索引的 ORDERS）：表本身、主键背后的索引、自建索引共三行。一张表会留下三行，别看到三行就以为删了三张表。

第 3 步：执行 FLASHBACK 把表带回来

FLASHBACK TABLE <模式名>.<原表名> TO BEFORE DROP;

实测输出：executed successfully，用时 14.307 毫秒 —— 不需要停业务、不需要备份文件、不需要归档。

如果这里报 [-9805]:Recycle bin is disabled. 说明回收站本来就没开，这条路不存在，回到第 1 步的判断，转第 8 步。

第 4 步：校验：行数 / 主键区间 / 汇总值

SELECT COUNT(*) AS CNT, MIN(ID) AS MIN_ID, MAX(ID) AS MAX_ID, SUM(AMT) AS AMT
  FROM <模式名>.<表名>;

-- 闪回后回收站里对应的行应该已经没了
SELECT COUNT(*) FROM DBA_RECYCLEBIN WHERE ORIGINAL_NAME = '<表名>';

实测输出（DROP 前 200 行 / SUM=201000）：闪回后 CNT=200 / MIN_ID=1 / MAX_ID=200 / AMT=201000，回收站对应条目已清空（RECYCLEBIN_LEFT=0）。三项与 DROP 前完全一致。

第 5 步：把 BIN$ 索引名与约束名改回来

-- 先看现在是些什么名字
SELECT INDEX_NAME, INDEX_TYPE, STATUS FROM DBA_INDEXES
 WHERE TABLE_OWNER = '<模式名>' ORDER BY INDEX_NAME;
SELECT CONSTRAINT_NAME, CONSTRAINT_TYPE FROM DBA_CONSTRAINTS
 WHERE OWNER = '<模式名>';

-- 改回业务原名（注意 BIN$ 名要加双引号）
ALTER INDEX <模式名>."BIN$33555496$0" RENAME TO <原索引名>;
ALTER TABLE <模式名>.<表名> RENAME CONSTRAINT "BIN$134218805$0" TO <原约束名>;

实测输出：闪回之后索引名变成了 BIN$33555496$0、INDEX33555494、INDEX33555495，主键约束变成 BIN$134218805$0。数据是对的、索引也是 VALID，但名字全变了。

业务代码里按名引用索引的地方会开始报错：DROP INDEX IDX_ORDERS_CUST、ALTER INDEX ... REBUILD、SQL hint 里写死索引名、按名比对的巡检脚本。这步不做，闪回等于只做了一半。

第 6 步：已经重建了同名表怎么办

-- 别删新建的那张表（那是二次事故），把回收到的那份落到旁边
FLASHBACK TABLE <模式名>.<表名> TO BEFORE DROP
  RENAME TO <新名_restored>;

实测输出：老数据 200 行落到 ORDERS_RESTORED，后来新建的那张表 1 行没动（NEW_TABLE_ROWS_STILL=1）。接下来慢慢比对、把数据搬回去，谁都不用再冒一次险。

第 7 步：三种彻底救不回来的情况

以下三种情况，回收站和备份都救不回来，只能靠业务侧补录或从下游同步源重新拉取：

  1. 回收站没开（RECYCLEBIN=0）且没有全库备份 —— 表的数据页直接被标记删除，无处可寻。
  2. 回收站已满被自动清理 —— 回收站有空间上限（RECYCLE 默认 300MB），超出后最老的对象会被自动清掉。
  3. 表被 DROP 后又建了同名表 —— 回收站里的旧对象名与新表冲突，闪回会报对象已存在，需要先改新表名（第 6 步的 RENAME TO 正是为此）。

第 8 步：兜底：从逻辑备份恢复

# 日常就要有这一步：单表或整模式导出（FILE 用全路径）
dexp SYSDBA/<密码>@localhost:5236 \
  FILE=/home/dmdba/bak/orders_backup.dmp \
  LOG=/home/dmdba/bak/dexp_orders.log \
  TABLES=<模式名>.<表名>

# 误删之后：把表导回来
dimp SYSDBA/<密码>@localhost:5236 \
  FILE=/home/dmdba/bak/orders_backup.dmp \
  LOG=/home/dmdba/bak/dimp_orders.log \
  TABLES=<模式名>.<表名> IGNORE=Y

实测输出（导出 → DROP 掉 → dimp 灌回）：导出 200 行 / 3.785 KB，导入后 CNT=200 / MIN_ID=1 / MAX_ID=200 / SUM_AMT=201000，与 DROP 前完全一致。

这是逻辑备份，不是物理备份 —— 它救的是"表结构 + 表数据"，不救索引名、不救权限、不救触发器以外的数据库对象。如果这都没有，就只能走备份时间点恢复那条更重的路了。

第 9 步：平时怎么做，才不用抢救

-- 1) 打开回收站（静态参数：scope=2 写配置文件，重启生效）
CALL SP_SET_PARA_VALUE(2,'RECYCLEBIN',1);
-- 重启实例后确认
SELECT PARA_NAME, PARA_VALUE FROM V$DM_INI WHERE PARA_NAME='RECYCLEBIN';

-- 2) 看回收站占用与保留策略（按需调，别让它无限涨）
SELECT PARA_NAME, PARA_VALUE FROM V$DM_INI
 WHERE PARA_NAME IN ('RECYCLEBIN','RECYCLEBIN_RETENTION','RECYCLE');

-- 3) 定期盘点回收站，确认没有"以为删了其实还占着空间"的对象
SELECT OWNER, ORIGINAL_NAME, DROPTIME FROM DBA_RECYCLEBIN ORDER BY DROPTIME;

实测参数（本版默认值）：RECYCLE=300（MB）、RECYCLE_POOLS=6、ENABLE_FLASHBACK=0、UNDO_RETENTION=90、RECYCLEBIN=0、RECYCLEBIN_RETENTION=0。

RECYCLEBIN=0 是这篇指南存在的原因。ENABLE_FLASHBACK=0 是另一个开关（管的是"闪回查询/闪回版本"，能看历史行、不能救 DROP 表），别和回收站混为一谈。
