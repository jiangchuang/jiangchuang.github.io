驱动日志里只有一个执行号，怎么找回那条 SQL 的执行计划

性能优化

三十秒版本。驱动日志里有 [EXEC_ID]: 67600。拿这个号去库里走三步，计划全文就出来了：

-- 第一步：执行号换 SQL_ID、逻辑读和原句
select exec_id, sql_id, n_logic_read, top_sql_text
from v$sql_history where exec_id = 67600;

-- 第二步：SQL_ID 换计划地址
select cast(pln_addr as bigint) from v$sql_plan where sql_id = 1607;

-- 第三步：把地址丢给函数
select sf_trace_dump_pln(pln_id => 140480814356576) from dual;

不用登服务器、不用 dump 文件、不用改代码，也不用在计划缓存里按文本猜哪条是你。

文中输出和数字都是在一台 CentOS 7 单机 DM8 上跑出来的（服务端 8.1.5.8，构建号 03134284552-20260414-322369-20221；驱动 DmJdbcDriver8.jar 8.1.4.200；表 5 万行）。服务端版本号是 DatabaseMetaData.getDatabaseProductVersion() 自报的，函数可用性以你库上 v$version 的构建号为准。

「昨天中午那条 SQL 慢，你给看看」

这话接过来，你手上通常只有一个执行号。

程序员翻日志，找到那条 800 毫秒的语句，然后要把现场交给你。他给的可能是 SQL 文本，也可能只丢一个数字，因为达梦 JDBC 驱动的日志里，每条 SQL 后面都跟着一个执行号：

[SQL   - 2026-11-19 12:00:43.103] tid:1 - [main] { conn-1, stmt-1 } executeQuery(String): rs-1;
  [PARAMS]: "select id, pad from T_ORDER where id between 100 and 120";
  [USED TIME]: 7.1721ms; [EXEC_ID]: 67601;

这个号是服务器给的。问题在于，大多数人以为它一会儿就没了，于是拿着它什么也做不了，只能回头问「你还记得是什么语句吗」。参数已经换了，语句也可能变了，一轮问答下来半小时过去了。

其实它还活着，而且活得比你想象得久。下面这条链能把它一路换成计划，全程在数据库里完成。

先确认一件事：你的版本有没有这个函数

SF_TRACE_DUMP_PLN 是达梦的系统函数，作用是按计划地址把缓存里的执行计划原样打出来。8.1.4.170 之后的版本才有，按官方社区的说法是 2025Q2 版本引入。一条命令确认：

select * from v$version;
LINEID     BANNER
---------- ---------------------------------
1          DM Database Server 64 V8
2          DB Version: 0x7000d
3          03134284552-20260414-322369-20221
4          Msg Version: 1
5          Gsu level(5) cnt: 102

第三行那个构建号，前 9 位 03134284552 里的版本段要能对到 8.1.4.170 或更高。对不上就先看文末「老版本怎么办」，那条路要多登一次服务器。

第一步：执行号换 SQL_ID、逻辑读和原句

一句话，一个字都不用改，把 67600 换成你手上的号：

select exec_id, sql_id, sess_id, sess_seq, time_used, n_logic_read, n_phy_read, top_sql_text
from v$sql_history
where exec_id = 67600;
LINEID  EXEC_ID  SQL_ID  SESS_ID              SESS_SEQ  TIME_USED  N_LOGIC_READ  N_PHY_READ  TXT
------  -------  ------  -------------------  --------  ---------  ------------  ----------  ------------------------------
1       67600    1607    140547514049216      705       206        2             0           select count(*) from T_ORDER where code='CODE500'

四个东西一次拿到，都值得看一眼：

  • SQL_ID 是 1607。它是这条语句在库里的身份证，比执行号稳定得多：实测同一句连跑 10 次、换个会话再跑，都是同一个 SQL_ID。但实例重启后会重新分配，别把它当永久主键。
  • N_LOGIC_READ 是 2。这条走了索引，只读两个页。
  • TIME_USED 是 206，单位是微秒，也就是 0.2 毫秒。而驱动日志里写的是 11.84 毫秒。差的这十几毫秒是客户端这一段：建连、硬解析、结果集在路上。两个数都对，口径不同，别拿它们互相打架。
  • SESS_ID 是 140547514049216，和驱动日志里那个 sessionID-0x7fd3c4a622c0(140547514049216) 是同一个数。这是一条独立的对账线索，怀疑执行号抄错时用它复核。

顺手把旁边那条也查出来，对比更直观：

2       67601    1608    140547514049216      705       3533       895           0           select id, pad from T_ORDER where id between 100 and 120

同一个连接、同一秒内，一条读 2 个页，一条读 895 个页。这条 between 查询走的是全表扫，5 万行全过一遍，计划在第四步能看到。

第二步：SQL_ID 换计划地址，一条 SQL 就够

v$cachepln 里确实没有 SQL_ID。我 desc 过，26 个字段，能定位计划的只有 CACHE_ITEM 和 SQLSTR。所以很多人到这里就转去按文本匹配，还得小心匹配到查询语句自己。

不用绕。V$SQL_PLAN 里 SQL_ID 和计划地址都在：

select sql_id, hash_value, pln_addr from v$sql_plan where sql_id = 49;
LINEID  SQL_ID  HASH_VALUE  PLN_ADDR
------  ------  ----------  ------------------
1       49      23576788    0x00007FC43D50EF38

PLN_ADDR 的类型是 VARBINARY(8)，打印出来是十六进制地址；而 SF_TRACE_DUMP_PLN 的 PLN_ID 是 BIGINT。中间要加一层 cast：

select cast(pln_addr as bigint) as pln_id from v$sql_plan where sql_id = 49;
LINEID  PLN_ID
------  ------------------
1       140480819031864

这个数就是 v$cachepln 里那条计划的 CACHE_ITEM，两个视图说的是同一个地址：

select cache_item, hash_value from v$cachepln where cache_item = 140480819031864;
LINEID  CACHE_ITEM          HASH_VALUE
------  ------------------  ----------
1       140480819031864      23576788

关系也干净：一个 SQL_ID 对应一行计划。我这边整张 v$sql_plan 17 行、17 个不同 SQL_ID，没有一对多。所以拿 SQL_ID 查，不存在「匹配到两条，哪条才是我」的问题。

想一步写完也行，把第一步嵌进去：

select sf_trace_dump_pln(pln_id => (
  select cast(p.pln_addr as bigint) from v$sql_plan p
   where p.sql_id = (select sql_id from v$sql_history where exec_id = 3101)
)) from dual;

这里更正一处。这篇最初写的是「SQL_ID 换不出计划，只能靠 SQL 文本」，理由是 v$cachepln 没有 SQL_ID 列。那句话只说了一半：我漏查了 v$sql_plan。上面这条路是实测过的，比文本匹配稳，以下面这条为主。

手上只有 SQL 文本、没有 SQL_ID

从文本直接找地址，跳过第一步：

select cache_item, substr(sqlstr, 1, 60) as s
from v$cachepln
where sqlstr like '%T_ORDER%CODE500%';
LINEID  CACHE_ITEM          S
------  ------------------  ------------------------------------------------------------
1       140545257176760     select cache_item, substr(sqlstr, 1, 60) as s from v$cachepln
2       140545257357784     select count(*) from T_ORDER where code='CODE500'

第一条是这条查询语句自己，因为它的文本里也带着 T_ORDER 和 CODE500 两个词。第二条才是你要的。这类自匹配几乎每次都会出现，看到两条不要慌，认出哪条是真的就行。

要更准就把 like 换成等值。注意 SQLSTR 末尾带分号，我实测长度 56 对应 55 个字符加一个 ;，漏掉分号一条都查不到：

select cache_item from v$cachepln
where sqlstr = 'select count(*) from T_SFP where id between 900 and 920;';

第三步：把地址丢给函数

CACHE_ITEM 就是一个整数地址，直接作为参数：

select sf_trace_dump_pln(140545257168568) from dual;

这个函数的参数名叫 PLN_ID，类型 BIGINT，所以也可以写成命名参数的形式，两者等价：

select sf_trace_dump_pln(pln_id => 140545257168568) from dual;

我是先试 pln_id => 1，报 [-2206]:Invalid parameter value，说明参数名认了、值不合法，才确信这个写法成立。传一个随便编的地址也是同样的报错，这一点在 FAQ 里说。

输出比较长，disql 里先 set long 100000，否则会被截断。完整的一段是这样：

*** 2026-11-19 12:02:01.818000000*** start dump the infos of pln[140545257168568].
	npln cache infos:
        scp cache
            type: 0
            over flow: 0
            disable: 0
            fixed number: 1
            ts value: 239
        type: 0
        hash val: 745726226
        schid: 150994945
        user id: 50331649
        obj id: 0
        --rs cache
        rs can cache: 0
        rs cache size: 0
        tables' size: 1
PLN_CREATE_TIME: 2026-11-19 12:00:42.000

SQL_STR:
select id, pad from T_ORDER where id between 100 and 120

PLN_CMD:
	0	savepoint
	6	dop_try_begin	0
	10	dop_try_begin	1
	14	sql 0 0
	24	nop
	26	jmp	67
	...

sqlnode[0]::::
1   #NSET2: [6, 1875, 68]
2     #PRJT2: [6, 1875, 68]; exp_num(3), is_atom(FALSE); INFO_BITS(0)
3       #SLCT2: [6, 1875, 68]; (T_ORDER.ID >= var1 AND T_ORDER.ID <= var2), slct_pushdown(1)
4         #CSCN2: [6, 50000, 68]; INDEX33555466(T_ORDER); btr_scan(1); need_slct(1)

end dump the infos of pln[140545257168568].

四段，按顺序读：

  1. 头部元信息：计划地址、哈希值、所属 schema。核对 pln[...] 里那个数和你要找的对不对，一眼就能看出拿错没有。
  2. PLN_CREATE_TIME：2026-11-19 12:00:42。这是计划生成的时间，不是 SQL 执行的时间。同一个计划被复用一百次，这里还是第一次生成的那个时间。想看执行时间，回第一步看 TIME_USED。
  3. PLN_CMD：计划指令序列，虚拟机码。平时不用读，怀疑优化器和你想的不一样时，它才是最终证据。
  4. sqlnode：人看得懂的计划树。#CSCN2 是全表扫，#SLCT2 是过滤，方括号里三个数依次是代价 6、预估行数 50000、预估行宽 68 字节。

计划里写的是 var1、var2，不是 100 和 120。因为驱动走的是参数化路径，计划缓存里存的是带变量的通用计划，绑定的实值不在这里。想知道具体绑定值，得回驱动日志的 [PARAMS]，那里有。

再看那条走索引的 count：

1   #NSET2: [1, 1, 48]
2     #PRJT2: [1, 1, 48]; exp_num(1), is_atom(FALSE); INFO_BITS(0)
3       #AAGR2: [1, 1, 48]; grp_num(0), sfun_num(1), distinct_flag[0]; slave_empty(0)
4         #SSEK2: [1, 1250, 48]; scan_type(ASC), IDX_ORDER_CODE(T_ORDER), is_global(0), scan_range['CODE500','CODE500']

#SSEK2 是索引范围扫描，scan_range['CODE500','CODE500'] 说明条件被收成了一个点查。这个形状配第一步的 N_LOGIC_READ=2，两边对得上，这条 SQL 没问题。

有一条更短的路，但多数时候走不了

如果目标会话开着 SQL 监控，V$SQL_STAT 里会直接有执行号和计划地址，一步到位：

select exec_id, sql_id, pln_addr, logic_read_cnt from v$sql_stat where exec_id = 68200;

问题在「开着」这两个字。MONITOR_SQL_EXEC 是会话级参数，默认 0。我实测过两种情况：

  • 目标会话没设这个参数，执行完就退出。换个会话拿 exec_id = 66802 去查 v$sql_stat，返回 no rows。
  • 想图省事用 sf_set_system_para_value('MONITOR_SQL_EXEC', 1, 0, 2) 改系统级，执行成功了，但新开的会话查 v$parameter 还是 0。改了不生效，属于静默失败，这个坑比报错更费时间。

所以这条路只适合「我自己开个会话复现一下」的场景。真拿到别人的执行号，还是走前三步，那三步不依赖任何监控参数。

另外实测到一个小细节：就算开了监控，PLN_ADDR 也可能为 NULL。我这边一条 select count(*) 的记录就是空的，而同批次另一条有地址。遇到 NULL 不要以为参数没生效，换个执行号或者走文本匹配那条路。

这条链断在哪

三个地方会断，提前知道比事后猜强。

一、计划地址会被回收。缓存里的计划受内存和淘汰策略管，地址失效以后再传进去，报 [-2206]:Invalid parameter value，不会告诉你「过期了」。所以这三个步骤最好一次跑完，别隔一顿饭。

二、按文本匹配会命中多条，能拿到 SQL_ID 就别走这条。同一条语句被不同用户、不同 schema 执行，可能各有各的计划条目；语句里带注释、空白不同，也会分裂成多条。「查询语句匹配到自己」的情况每次都发生。判断依据是看 SQLSTR 全文，别看前缀。有 SQL_ID 时走 v$sql_plan，一条对一行，没有这个烦恼。

三、缓存计划没有实际统计。这里是估算行数 50000，不是实际返回行数。达梦没有 EXPLAIN ANALYZE，敲了报 [-2007]:Syntax error。要真实数据，得用 set autotrace traceonly、ET(执行号) 或者 DBMS_SQLTUNE.REPORT_SQL_MONITOR，那几个都要在语句执行的那一刻抓，事后补不上。

换句话说，SF_TRACE_DUMP_PLN 解决的是「形状」，不是「耗时」。想知道钱花在哪个算子上，它给不了。

常见问题

执行号到底能活多久？

分两个地方看，别混。V$SQL_STAT 里的是内存现场，会话结束或者监控没开就没有了，这也是「一会儿就刷掉」这个印象的来源。V$SQL_HISTORY 是另一套东西，它由参数 SQL_HISTORY_CNT 控制保留条数，我这台库上是 10000，用环形覆盖的方式滚动。也就是说，只要没被一万条新记录挤掉，昨天的执行号现在还能查。

我实测跨会话、隔了两分钟再查 65902，照样能出 SQL_ID 和逻辑读。重启这条路后来补测了：实例重启后 V$SQL_HISTORY 是空的，SQL_ID 也重新分配，同一句 SQL 重启前是 1682，重启后变成 10。所以它终究是内存里的东西，别拿它当长期审计用。

报 [-2206]:Invalid parameter value 是什么意思？

两种可能，都指向同一个原因：这个地址在缓存里不存在。要么抄错了，要么计划已经被回收。先回第二步确认这个地址还在不在，select cache_item from v$cachepln where cache_item = 你的地址，返回空就说明过期了，只能重跑那条 SQL 让它重新生成计划，再按新地址取。

为什么 v$sql_stat 一条都查不到？

九成是 MONITOR_SQL_EXEC 没开。检查一下当前会话：

select name, value from v$parameter where name = 'MONITOR_SQL_EXEC';

要 1 才有记录。开法：call sf_set_session_para_value('MONITOR_SQL_EXEC', 1);，然后在同一个会话里执行目标 SQL。换个会话查不到别人的，这是实测过的。

能不能只用 SQL_ID 拿计划？

能，走 v$sql_plan。这个视图里 SQL_ID 和 PLN_ADDR 在同一行，cast 成 bigint 就能直接喂给函数。我最早写这条「不行」，是只 desc 了 v$cachepln、没查 v$sql_plan，属于漏查，别按老印象记。v$sql_stat 那条也能拿，但它要先开会话级监控，不如 v$sql_plan 稳。

第一步查出来的 N_LOGIC_READ，和 autotrace 的对得上吗？

口径一样，都是页数，但不含物理读，这是达梦和 Oracle 相反的地方。同一批测试里我用 set autotrace traceonly 和这个视图对比过，数字一致。要注意的是这个字段统计的是那一次执行，不是累计值，拿它当「这条 SQL 平时读多少页」用会偏小。

老版本没有 SF_TRACE_DUMP_PLN 怎么办？

用 plndump 事件，输出到服务器的 trace 文件，要登机器去 cat：

alter session set events 'immediate trace name plndump level 140545257168568, dump_file ''plndump_test.trc''';

文件落在 TRACE_PATH 下，路径用 select * from v$dm_ini where para_name = 'TRACE_PATH' 查。文件名只能给纯名字，给绝对路径会报存在父目录引用，这个限制官方社区文档里也写了。内容和新函数打出来的一致，只是多了一次登录和一次找文件。

只有 SQL 文本，没有执行号，还能用吗？

能，按文本去 v$cachepln 找地址，写法在第二步末尾那个小节。代价是拿不到 TIME_USED 和 N_LOGIC_READ，那两项只在执行记录里。

换一个达梦版本还成立吗？

函数是内置的，不在数据字典里，我用 sys.sysobjects 查它的名字是零行，all_arguments 也是零行，所以拿不到官方签名，全靠试。我在 8.1.5.8 上确认了参数名 PLN_ID 和 BIGINT 类型。换版本请先跑一次 select sf_trace_dump_pln(pln_id => 1) from dual，报 -2206 说明函数在、参数名对；报「函数不存在」就得换回 plndump 那条路。

最后

这个用法本身没什么技术含量，两三条 SQL 而已。它改变的是取证的时间成本：以前要知道一条 SQL 用了什么计划，得登服务器、开事件、找文件、下载、打开；现在在执行号还在的时候，三条 SQL 就完事，人还在电话上就能回话。

对程序员来说这也是好事。他不用为了让你看计划，专门去加日志、发一次版。把执行号和诉求一起发过来，你这边就能自己查。

执行号从哪来。驱动日志里的 [EXEC_ID] 是驱动自己打的，开法见这篇：达梦 JDBC 打印真实执行计划：一个类加一个连接串参数，业务代码不用改。那篇讲怎么让每条 SQL 自己开口，这篇讲它开口以后怎么顺着线索往下查。

N_LOGIC_READ 那个数怎么判读、多少算多，见：达梦怎么看逻辑读：三步拿到那个数字，然后让它变小。

卡在某一步了？

先确认三件事：服务端构建号在 8.1.4.170 之后、执行号是 v$sql_history 里真能查到的、计划地址是刚从 v$cachepln 取出来的。还对不上，把这三样发我：卡在第几步、报错原文、v$version 的第三行。不用发库里的数据。
