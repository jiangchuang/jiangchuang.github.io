AI 协作的两把钥匙：判断与验证

工作方法

你有没有过这种时候：AI 给了三个方案，看着都挺像样，但你不知道该信哪个。或者它把达梦某个参数的默认值编得一本正经，等你照着敲进去才发现不对。

这篇不涉及达梦的具体命令，讲的是「怎么跟 AI 协作才不吃亏」，案例来自达梦现场的活。

缘起是一句原话：「不是黑盒子，要用好一个东西，起码要知道它的基本原理，这是未来 AI 时代拉开差距的地方。」下面是从这句追问出来的全部结论。

一、先纠一个说法：不是「懂原理 vs 能验证」

有个流行说法是「AI 时代拉开差距的不是懂原理，是能验证」。这句话只对了一半，而且把互补关系说成了替代关系。

组合结果
有原理，没验证纸上谈兵——想得对，落不了地
有验证，没原理形式主义——验得勤，抓不住要害
两者都有才叫能力

原理 × 验证 = 能力。乘法，不是加法。任一为零，结果为零。

三条推导：

  1. 稀缺性位移，不是价值下降。类比计算器：心算没变得不重要（估算、检查按错全靠它），但「算得快」不再是竞争力。原理在 AI 时代也是位移——从「记得住」变成「用得上」。
  2. 验证是原理的函数。你知道 %util 恒等式会骗人，才能验出「盘饱和了」是假的；你知道达梦驱动自带 30 秒 socket 超时，才能验出「传 --timeout 3 就生效」是假的。没有原理，连「该验什么」都不知道。
  3. 验证的前提是有 oracle（一个能告诉你「什么算对」的东西）。通用领域 oracle 现成（文档全、报错能搜到），黑盒验就行；达梦这种冷门领域没有 oracle，原理是你自己造 oracle 的唯一材料。

一句话：验证能替代「知道答案」，替代不了「知道该怎么验」。

二、失去原理的代价：验证会退化成「形式验证」

没原理的人验什么有原理的人验什么
V$DM_MAL_INI 里有记录 → 配置对了有记录 ≠ 生效，还要看 MON_CONFIRM 与 login 时序
退出码 0 → 成功退出码 0 可能是 timeout 124 被掩盖，要看输出里有没有「迁移完成.」

没有原理支撑的验证，会伪装成「我已经验证过了」——这种损失最难发现，因为它看起来最严谨。

三、判断路径：六步

样本是一次真实决策：判断某个知识仓该不该建定时同步。全程可复核。

步动作一句话
1先抓名词「本地」指哪台机器？
2先看现状它是活仓还是快照？查 git log
3验前提这结论成立需要什么条件？条件在不在？
4找宪法这事有无既定规则？规则优先于偏好
5让规则做决定结论要能指回条款
6给反方留门什么条件下我会改判？

第 6 步是分水岭：好的判断不是「我选 A」，是「我知道什么条件下我会改成 B」。
审 AI 的用法：它每次说「不该做 X」，你问一句「什么条件下你会改判」。答不上来的，多半在凭偏好说话。

四、验证三层：按场景选，不必层层做满

层问法耗时用在哪
L1 来源「这条能指回哪个源？」手册第几章 / 哪个实测环境30 秒每次都问
L2 复现「给我一条能跑的命令」→ 自己重跑2 分钟要动手的活
L3 边界「什么条件下这条会失效？」换版本还成立吗5 分钟客户交付、方案定稿

判据很简单：不要每件事都做到三层（会累死），也不要永远停在一层（那是赌）。

五、AI 为什么会幻觉：四条结构性成因

  1. 本质是「预测下一个词」，不是「查数据库」。优化的是「看起来像正确答案」，不是「是正确答案」。这两件事在小众领域会分叉。
  2. 高频模式压倒低频事实。达梦语料量远小于 MySQL，细节记不牢，模型就用「一般数据库常识」去填坑。这就是报错小本本存在的根本原因。
  3. 没有天然的「我不知道」信号。人不确定会犹豫；模型输出里「编一个像样的」往往比「说不知道」更顺畅。所以「未实测」必须刻意标注。
  4. 上下文会自我污染。前面聊错的一句，后面会被当成事实继续推。这就是「先查文件」有效的原因——用磁盘上的事实覆盖模型脑子里的印象。

三条推论：越冷门越要查（达梦 > MySQL）；越具体越要查（默认值 > 大致原理）；越自信越要查（语气笃定是训练出来的，不是知识带来的）。

六、哪些该学，哪些不该学

值得学不该学（AI 特有，人硬学反受害）
先抓名词 / 先看现状 / 找权威源
事实·判断·未实测分开说
能跑的不猜 / 失败先认 / 给下一条命令		 并行读一堆文件（人读完记不住，反而碎片化）
穷举所有方案再筛（人时间只够深挖 1 种）
快速产出再迭代（人的沉没成本高）
什么都要留痕（变成表演性勤奋）

差别在哪？AI 的很多优势来自「成本低」，而你最大的约束恰恰是成本。

七、两周练习：三条，不额外花时间

  1. 每次 AI 给领域结论，挑一条问「指回哪个源」——练 L1。
  2. 每周挑一个判断，问「什么条件下你会改判」——练第 6 步。
  3. 自己做决定时，先写一句「我的依据是 ___」——把隐性判断显性化。

最难坚持的是第 3 条：前两条是「审别人」，第 3 条是「审自己」。

八、输出分级：不每轮都贴执行计划树

「每次回答都加一棵计划树」成本收益不对等，会退化成表演。改成按级别触发：

级别触发做法
A 必带不可逆操作 / 跨机交付 / 反直觉结论 / 客户交付末尾三行「依据 · 实测 · 排除」
B 可选分析、调研、方案一行来源
C 不带事实问答、查询直接给答案
—— 依据：SCHEMA.md §1 三层职责｜实测：git log 仅 1 条提交｜排除：本机无源目录

为什么不是树：树记流水账，锚点只记「改变了结论的三件事」，信息密度更高。它的价值也不是审计，是教学——看多了会长出模式识别。

九、一页速记

判断六步验证三层 / 幻觉三查
① 抓名词 ② 看现状 ③ 验前提
④ 找宪法 ⑤ 规则做决定 ⑥ 给反方留门		 L1 来源 · L2 复现 · L3 边界
越冷门 / 越具体 / 越自信 → 越要查

十、常见问题

Q1：精力全给验证，原理会荒废吗？

会，而且是非线性的：验证能力到 80 分就够用（边际收益递减），原理是复利资产（一个原理能解释一百个现象）。配比建议：日常 90% 验证 + 10% 追原理，但那 10% 决定上限。而且原理不要靠「系统学习」，靠每次验证失败后往回追一层——有动机、有边界、有验收。

Q2：格式能解决信任吗？

不能。真正让「凭什么信你」成立的只有三条：可复现（给的命令能重跑出同样结果）、可证伪（测不了就写「未实测」）、认账（错了先认）。锚点只是这三条的索引。

Q3：为什么这篇反复强调达梦？

因为它是「没有现成 oracle」的典型场景。在通用编程里，黑盒验证能替代大半原理；在达梦里不行——你得自己造判据，造判据要原理。

Q4：这套是定论吗？

不是。第一版曾写「差距不在懂原理，在能验证」，被三层追问戳破后才改成乘法模型。文里「四种难的占比」「练习法」都是经验估计，没有统计。你按它试几次，哪条不成立就回来告诉我。
