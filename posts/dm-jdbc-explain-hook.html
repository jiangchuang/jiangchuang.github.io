达梦 JDBC 打印真实执行计划：一个类加一个连接串参数，业务代码不用改

性能优化

三十秒版本。把下面那个 PlanLogger 类放进项目（四十行），连接串末尾加 ?custom_filter=dm.debug.PlanLogger，之后这个连接上每执行一条 SQL，控制台就会打出它的执行计划、逻辑读、物理读和服务端耗时。业务代码一行不动，不用重新发版，开关就在配置里。

文中输出和数字都是在一台 2G 内存的单机 DM8 上跑出来的（Linux，8K 页，30 万行表，驱动 DmJdbcDriver8.jar 8.1.4.200），不是抄的。驱动自报 124 个连接属性，里面没有任何叫 printPlan / showPlan 的开关，custom_filter 是唯一那条缝。

「这条 SQL 线上慢，你 EXPLAIN 一下」

这句话听着简单，做起来有几步都要卡人。

日志里只有一句 SQL 和一个 800 毫秒，参数是问号。你要 EXPLAIN，得先把参数换成实值，再找一个库去跑。测试库的表只有两万行，生产有三百万，计划根本不是一回事，跑出来的东西没法用。想去生产库跑，得有权限，还得挑时间，最好别在业务高峰。

那就不如在自己代码里打一下。于是你打开 IDE，在 DAO 层加几行日志，连测试环境验证，提 MR，等评审，合并，发版。为了看一条 SQL 的计划，走了一整套发布流程。第二天那条 SQL 又慢了，这次参数不一样，你还得再来一遍。

MySQL 那边至少有个慢查询日志，达梦这边也有服务端的 SQL 日志，但那是 DBA 的地盘，拿计划还得再折腾一轮。所以这件事真正的痛点不是「怎么拿到计划」，是「怎么在不改代码、不发版的前提下拿到，而且下次还能用」。

下面就是这个答案：让驱动自己在每次执行后把计划打出来。

第一步：把这个类放进项目

整个类四十行，只有 afterExecute 一个有内容，其余三个钩子照原样返回。

package dm.debug;

import dm.jdbc.driver.DmdbConnection;
import dm.jdbc.filter.custom.ICustom;

import java.sql.Statement;
import java.util.Map;

public class PlanLogger implements ICustom {

    // 防止 getExplainInfo 内部又触发一次钩子，造成递归
    private static final ThreadLocal<Boolean> IN = new ThreadLocal<Boolean>();

    public boolean beforePrepare(Map<String, Object> m) { return true; }

    public void afterPrepare(Map<String, Object> m) { }

    public boolean beforeExecute(Map<String, Object> m) { return true; }

    public void afterExecute(Map<String, Object> m) {
        if (Boolean.TRUE.equals(IN.get())) return;
        Object o = m.get(KEY_STATEMENT);
        if (!(o instanceof Statement)) return;
        Statement st = (Statement) o;
        try {
            IN.set(Boolean.TRUE);
            DmdbConnection dc = st.getConnection().unwrap(DmdbConnection.class);
            String info = dc.getExplainInfo(st);
            if (info == null) return;
            System.out.println("==== PLAN ==== " + m.get(KEY_SQL));
            System.out.println(info.trim());
        } catch (Throwable t) {
            System.out.println("[PlanLogger] " + t);
        } finally {
            IN.remove();
        }
    }
}

三个地方容易卡住，先说在前面：

  • 类必须是 public，并且有公开的无参构造。驱动是用 Class.forName(名字).newInstance() 加载它的。
  • 包名随意，但要和连接串里写的一致。上面是 dm.debug，你换成自己项目的包也行。
  • 编译期要能访问驱动 jar，因为用到了 DmdbConnection 和 ICustom。Maven 依赖就是你项目里那个达梦驱动。

把 System.out.println 换成你项目的 logger 更合适，这里用标准输出只是为了让例子能直接跑。

第二步：连接串加一个参数

jdbc:dm://127.0.0.1:5236?custom_filter=dm.debug.PlanLogger

原来的连接串如果要带别的参数，继续用 & 接在后面：

jdbc:dm://127.0.0.1:5236?user=SYSDBA&custom_filter=dm.debug.PlanLogger

就这样，没有别的动作。不用注册驱动属性，不用改 dm.ini，不用重启数据库。想关掉，把这一段删了重启应用即可。这句话的意思也是：它是个启动期参数，改完得重连才生效。

第三步：看输出

4         #SLCT2: [34, 11250, 4]; (T_ORDER.ID >= 100 AND T_ORDER.ID <= 200)
5           #CSCN2: [34, 300000, 4]; INDEX33555466(T_ORDER); btr_scan(1)

#CSCN2 一出，全表扫，逻辑读从 772 变成 4540。这两个数字放在一起，比任何「优化建议」都直接。

它为什么能成立

达梦驱动有一百多个连接属性，我把它全部倒出来看过，和「看 SQL 干了什么」相关的只有三组：logLevel、statEnable、custom_filter。前两个都不给计划。

做法拿到什么拿不到什么
?logLevel=all每条 SQL 文本、每一步的客户端耗时没有计划。实测日志 71KB，grep 计划关键字 0 命中
?statEnable=trueCSV：SQL、执行次数、累计耗时、单次峰值、行数没有计划，也没有逻辑读
custom_filter计划 + 逻辑读 + 物理读 + 服务端耗时要写一个类

custom_filter 做的事很朴素：驱动在每次执行前后回调你的类，把 Statement 对象交给你。你拿着它调 getExplainInfo，等于在「刚执行完的这一刻」问驱动要计划和统计。它不重跑 SQL，因为计划早就在驱动里了，统计也是服务端刚刚返回的。

哪些语句能抓到

四种写法我都试过，都能出计划和统计：

写法结果说明
Statement.executeQuery(String)能计划里能看到字面量条件
PreparedStatement能条件显示为 exp_param(no:0)，看不到绑定的值
UPDATE能计划首行是 #UPDATE
DELETE能计划首行是 #DELETE

最后一行那条 UPDATE 我顺手看了一眼：update ... where id = 100，主键没建，走了全表扫，4589 次逻辑读。这种「以为按主键更新、其实全表扫」的写法，平时没人会去 EXPLAIN，日志里只会显示它花了 11 毫秒，因为表还在内存里。等表大了，它才会突然变成慢查询。

三个坑

一、计划里的行数是估的。上面那个走索引的例子显示 7500 行，实际返回 300 行。达梦没有 EXPLAIN ANALYZE，敲了会报 [-2007]:Syntax error，所以「每个算子实际处理了多少行」这个数拿不到。计划看形状，统计看真实代价，两个结合着读。

二、每次执行多一次往返。取计划本身是重新发一次 EXPLAIN 请求（只解析、不执行），所以每条 SQL 会多一个网络来回。我在本机环回上测过，四组配置的稳态耗时都在 1~3 毫秒，测不出差别；如果应用和数据库跨机房，这个差额就是每次的 RTT，高频接口上要算这笔账。

三、它会打印所有 SQL。一个请求进来可能有几十条语句，包括框架自己的。真要用在生产，得加条件，别全量打。

常见问题

取计划会不会把 SQL 又执行一遍？

不会。我用 V$SQL_HISTORY 的条数对比过，调用前后都是 12 条，没有新增。如果它真的重跑，慢 SQL 会慢一倍，那这个功能就没法用了。

会不会影响事务？

不影响。关掉自动提交、插一条不提交，调完取计划再 rollback，数据正常消失。取计划不碰事务状态。

统计里的 exec time 是服务端还是我这边等的？

服务端。它只算数据库执行这一段。用户实际等的时间还要加上网络往返和结果集传输。实测同一条 SQL，服务端 1.1 毫秒，客户端从执行到遍历完 16.6 毫秒，差的那十几毫秒是 37KB 结果集在路上。

生产上能一直开着吗？

不建议全量常开，理由不是它慢，是它吵。比较稳的做法是加个开关，只在排查期打开，或者只打慢的：

private static final ThreadLocal<Long> T0 = new ThreadLocal<Long>();

public boolean beforeExecute(Map<String, Object> m) {
    T0.set(System.nanoTime());
    return true;
}

public void afterExecute(Map<String, Object> m) {
    Long t0 = T0.get();
    if (t0 == null) return;
    T0.remove();
    long ms = (System.nanoTime() - t0) / 1000000;
    if (ms < 500) return;          // 只关心 500ms 以上的
    // 下面再接 getExplainInfo
}

注意这里量的是客户端感知到的时间，包含了取计划和网络，和 Statistics 里那个服务端时间是两个口径，别混着比。这段是思路，我没有单独跑过压测，标在这里。

能不能顺便打印参数值？

钩子的 map 里有 params 这个 key，但我没细验它的格式。而计划里绑定变量只显示 exp_param(no:0)，所以想知道「具体哪个参数慢」，得靠你自己在 beforeExecute 里把参数记下来，跟 SQL 一起打。这一块我没做完整实现，不写结论。

Tomcat 或 Spring Boot 里能直接用吗？

未实测。风险在类加载器：驱动是用自己的 ClassLoader 去 Class.forName 你的类，如果驱动在容器的公共 lib 里、你的类在应用的 WEB-INF/lib 或 fat-jar 里，可能找不到。稳妥的判断办法是在目标环境启动一次，看有没有 ClassNotFoundException；真遇到，把这个类跟驱动放进同一个加载域。

换个达梦版本还成立吗？

getExplainInfo 和 ICustom 都是驱动里的接口，不是标准 JDBC，文档里也没承诺不删。我在 8.1.4.200 上验证通过，换版本请重新跑一次：只要 dc.getExplainInfo(st) 还能返回带 Statistics 的字符串，这套就还能用。

最后

这个方案的价值不在技术含量，在于它把「看计划」这件事从一次发布流程，变成了一个配置项。以前你要为一条 SQL 走一遍 MR，现在改配置、重启、看完、改回来，五分钟。

顺手也能看出别的：一个平时没人注意的更新语句走了全表扫，一个接口里其实发了四十条 SQL，某个查询的逻辑读是邻居的十倍。这些东西不会报错，也不会进慢查询日志，只有在每条 SQL 都自己开口的时候才看得见。

想先把「这条 SQL 到底读了多少页」弄明白，看这篇：达梦怎么看逻辑读：三步拿到那个数字，然后让它变小。那篇讲三个入口和判读方法，这篇讲怎么让它自动发生。

卡在某一步了？

先确认三件事：类是不是 public 且有无参构造、连接串里的包名和类名是否完全一致、编译时 classpath 里有没有驱动 jar。还对不上，把这三样发我：卡在第几步、报错原文、驱动版本（DmJdbcDriver8.jar 还是别的）。不用发库里的数据。
