达梦 SQL 日志怎么读：把日志里的 ? 还原成真实参数

工具

📋 想照着敲？这篇有 交互操作版——步骤卡片导航、命令一键复制，现场对着敲更顺手：打开交互操作版 →

本文讲的工具是 dmsqlq，自研、单文件、开源之前先放二进制。下面每条命令和每个输出都是本机实跑取的，没有改写、没有补全。性能数字标了样本来源，能自己复核。

先说结论：让你复现不了现场的，不是日志太难，是参数没了

客户说"早上那条单子查不出来"，你去翻 SQL 日志，看到的是这个：

[SEL] SELECT * FROM t_rim_invoice WHERE fbill_id = ? AND status = ?  EXECTIME: 18.4(ms)

两个问号。fbill_id 是什么、status 是几，日志里这句话本身没写。

但 DM 的 SQL 日志其实把它记在另一行——紧接着的 PARAMS(SEQNO, TYPE, DATA) 行，靠时间戳和会话/语句句柄跟语句配对：

2026-09-10 09:00:00.000 (EP[0]{sess:0x7f100a,user:SYSDBA,stmt:0x2010,...}) PARAMS(SEQNO, TYPE, DATA)={(1, VARCHAR, 'dac000000'),(2, INT, 0)}
2026-09-10 09:00:00.000 (EP[0]{sess:0x7f100a,user:SYSDBA,stmt:0x2010,...}) [SEL] SELECT * FROM t_rim_invoice WHERE fbill_id = ? AND status = ?  EXECTIME: 18.4(ms)

所以能不能还原，只取决于两件事：日志里有没有那行 PARAMS（采集侧配的），和工具愿不愿意在参数值本身就带 ? 时继续往下填。第二件是很多工具翻车的地方，后面「和官方 DMLOG 怎么选」里说。

四条命令，从「上不了手」到「能交付」

下面第四条只是同一个命令换个参数。所有命令里的目录改成你自己的，其余照抄。

第 1 步：确认日志在哪，别认错文件

日志默认在实例目录的 log 下：

ls /opt/dmdbms/data/DAMENG/log/dmsql_*.log

同目录下还有另外两种日志，名字很像但完全不是一回事：

文件名是什么
dmsql_*.log要的就是这个——SQL 日志，带语句、耗时、参数
dm_*.log实例事件日志（启停、切换、报错），没有 SQL
dmtrc_*.log跟踪日志，另一套开关

机器上一个 dmsql_*.log 都没有？说明 SQL 日志没开，或者开了但没采到——先看后面「报告能不能信」那一节的采集体检，别急着换工具。

第 2 步：先扫一眼，不出文件

dmsqlq /opt/dmdbms/data/DAMENG/log -S

-S 是大写，意思「只打到屏幕」；-s 小写会额外生成一份 HTML 报告并用浏览器打开。实际输出（样例日志，600 条语句）：

dmsqlq 2.37 统计报告   2026-10-31 00:45:14
────────────────────────────── 概览 ──────────────────────────────
  ★ 头号问题：累计耗时最高的是一类语句（600 次 / 累计 18.03s，
    占语句总耗时的 89.2%）—— 从它开始优化收益最大。
  日志文件         1 个（0.2 MB）
  SQL 事件         686 条
  参数还原         600 成功 / 86 待还原  (87.46%)
  扫描耗时         7ms → 36 MB/s
  日志时段         2026-09-10 09:00:00 → 09:09:59（跨度 10.0 分钟）
────────────── 优先优化推荐 Top2（按影响占比排序） ───────────────
    1 [优先] 影响占比 89.2%  次数 600  平均 30ms  累计 18.03s
      问题信号：SELECT * 取全字段（直接查基表）
      建议动作：只取需要的列 —— 覆盖索引时才可能免回表
      语句样例：SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000000' AND status = 0

注意这份报告排的是 累计耗时占比，不是「单次最慢」。一天只跑一次的 8 秒慢查询，不该排在一个每分钟跑 60 次、每次 200ms 的查询前面——后者一天耗掉的小时数才是真的。

第 3 步：把 ? 换成真实值，导出能直接执行的 SQL

dmsqlq /opt/dmdbms/data/DAMENG/log -o out.sql

out.sql 里长这样：

-- 2026-09-10 09:00:00 · [SEL] · 0.1ms · SYSDBA, · trxid:3816438, · SAMPLE
SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000000' AND status = 0;

-- 2026-09-10 09:00:00 · [UPD] · 0.5ms · SYSDBA, · trxid:3816438, · SAMPLE · /*未找到匹配参数: 占位符2个*/
update ACCOUNTS set BALANCE = BALANCE + ? where ACCT_ID = ?;

两条对照着看就懂了：第一条参数填好了，可以直接贴进 disql；第二条工具自己承认「没找到参数」，而不是编一个值糊上去。

这一点值得单独说：「没还原」和「还原错了」是两种完全不同的后果。前者你知道要手工补；后者你会拿着一条假 SQL 去复现一个根本不存在的现场，然后得出完全错误的结论。所以还原不了的语句原样留 ?，注释头里写清占位符个数。

第 4 步：只要慢的，出交付清单

dmsqlq /opt/dmdbms/data/DAMENG/log -m 1000 -B 20 -o slow.sql

-m 1000 是耗时下限（毫秒），-B 20 是最多取 20 条。实际输出（样例取最慢 3 条）：

-- 2026-09-10 09:09:59 · [SEL] · 60ms · SYSDBA, · trxid:3816637, · SAMPLE
SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000599' AND status = 5;

-- 2026-09-10 09:09:58 · [SEL] · 59.9ms · SYSDBA, · trxid:3816637, · SAMPLE
SELECT * FROM t_rim_invoice WHERE fbill_id = 'dac000198' AND status = 0;

要发给开发商或客户当优化清单，加 -e 交付_202609.xlsx 直接出 Excel，已经按累计耗时降序排好优先级——省掉你在 Excel 里手工排序那一小时。

报告能不能信：三个自检点

一、先看「采集缺口」，这是「查不出来」的第一嫌疑

日志里显示「锁等待 0 次」，是真的没锁竞争吗？大概率是没采集到。工具会把这件事挑明，不让你误判：

  采集缺口   缺位号 29：本批日志无事务/锁事件行（TRX: / DLCK / LOCK_TID 全为 0）
             → 「锁等待」「长事务」「TPS」是没采集到，不是没发生

判据很硬：29 位号一旦开启，事务事件行必然大量出现，不可能恰好是 0。要这个维度，就在 sqllog.ini 的 SQL_TRACE_MASK 里打开 29 重采；短期替代是在库上查 V$TRXWAIT / V$LOCK。

顺带它还会做一份采集配置体检：缺 28 就没有参数行（还原率直接归零）、缺 27 没有原始语句、缺 23 没有报错语句。这几个位号记不住没关系，报告会直接告诉你缺哪个。

二、还原不了的，它明说，不装

/*未找到匹配参数: 占位符2个*/ 这行注释就是自检点。看到它，说明这批日志的 PARAMS 行缺失或被截断，不是工具坏了——回去查采集配置（位号 28），或者确认日志有没有被跨文件截断。

三、排序口径是「累计」，不是「单次最慢」

前面说过一次，这里再强调：如果你要的是「哪条 SQL 最拖垮系统」，累计耗时才是答案；如果你要的是「哪条 SQL 最慢」，用 -m 卡耗时下限。两个问题不一样，别拿一个答案去回另一个。

和官方 DMLOG 怎么选

先把话说清楚：DMLOG 是这条路上的先行者，从零到一把「SQL 日志能分析」这件事做成了。后来者（包括 dmsqlq）都是站在它提出的思路和口径上往前走的。所以下面只讲形态差异，不是谁替代谁。

维度官方 DMLOG 8.183dmsqlq
运行方式要一个 DM 分析库（32K 页）+ dmlog.properties + JDBC 连接单个二进制，dmsqlq . 就完事
结果落地在被分析的库里 DROP / CREATE 6 张分析表只写 SQL 文本文件，不落库
参数值本身含 ?整条放弃（同一批现网日志实测还原率 10.9%）继续还原（同批 97.8%）
参数值里带逗号会静默切掉前缀，仍标记为成功实测 14.9 万条含逗号/含引号的值全部完整

怎么选：要长期建库做趋势分析、本来就有专门的 analys 库 → DMLOG 那套仍然合适；要临时拿一份现网日志、几分钟内出结论、而且绝不能在生产库上建表（尤其不能出现 LOG_COMMIT 同名被 DROP 的风险）→ 用不落库这一支。

没做的事也说清楚：本次没有对 DMLOG 做计时实测，所以这里不引用任何耗时对比，只比有实测支撑的维度。

三个场景，对号入座

场景一：现场救火，只有一台能连的机器

把日志目录整个拷出来（或直接在库机上跑），dmsqlq 目录 -S 三十秒看结论。这时候最怕的是「为了分析先建个库」——现网不允许，也没时间。

场景二：给客户交优化清单

-m 200 -B 50 -e 交付.xlsx，按累计耗时排好序，附上每条的真实参数。客户拿着这份清单能自己去改索引、改 SQL，不用你再口头解释「那个时间段那条语句」。

场景三：长期观察，日志堆了几十 GB

直接喂目录或压缩包，-j 4。它会按文件并行，压缩包内的条目也并行——这一点手工脚本很难做对，因为 gzip 本身是串行流，能重叠的只有「解压」和「解析」。

常见问题

单个大日志，开 -j 30 会快很多吗？

不会。并发只作用于多个文件或压缩包内的多个条目；单个大文件开满核也没用（实测 -j 1 与 -j 30 同速）。

它会不会改我的库？要不要装 Java / .NET？

都不会，都不用。单文件、零依赖，不连数据库、不建表、不联网。你可以把它拷到一台完全隔离的机器上跑，只要有日志文件。

记不住参数怎么办？

直接敲 dmsqlq 不带参数，就是交互向导：五问（日志在哪 / 要什么结果 / 时间范围 / 耗时下限 / 操作类型），每一步回车就是推荐值，最后把等效命令行打印出来，下次照着敲。TAB 补全首次交互运行时自动装好，选项和路径都能补。

为什么报告里有些语句没有 EXECTIME？

说明这条语句在日志里没有执行完成的行（例如采集期间实例重启、或语句还在跑）。这类不会被算进耗时统计，但会出现在事件计数里，看起来「条数对不上」是正常的。

Windows 上用，路径要怎么写？

反斜杠和正斜杠都认：dmsqlq D:\dmsql_log -s 和 dmsqlq D:/dmsql_log -s 等价。路径里有空格就加引号。

能不能只处理某一段时间？

能，--from / --to 给时间范围（YYYY-MM-DD HH24:MI:SS）。只关心某类操作就加 --ops SEL（或多选 SEL,UPD）。

最后

这个工具的全部价值只有一句话：让「日志里那句话到底在执行什么」这个问题，在三分钟内有个能执行的答案，而不是让你在几百万行里手工捞参数。

它做不了的事也说清楚：它不会替你判断该加什么索引，也不会告诉你这条 SQL 业务上该不该存在。报告给的是证据和优先级，判断还是人做。

用着有问题、或者你手上的日志它读不动，提个 issue，把 --version 的输出和报错原文贴上就够定位。这类问题基本都能修，而且修完别人也能用。
