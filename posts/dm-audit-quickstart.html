达梦审计怎么开：5 条命令能抄，先知道它记不到什么

日常运维

测评问到「安全审计」，要的不是一句「开了」，是能当场查出来的一条条记录：谁、什么时间、从哪来、做了什么、成没成功。

达梦内置审计能给出这些。麻烦在配完那一步——规则配上去了，回头去查记录是空的，看着像没生效；换个账户查，直接报无权限。我第一次就是这么卡住的，还差点把「再配一遍规则」当成解决办法。

这篇给两样东西：5 条能直接粘的命令；以及这 5 条记不到什么。前者让你十分钟内交差，后者让你在测评老师追问「那插入呢」的时候不至于当场翻车。

实测环境：DM8 企业版单机，构建号 03134284488-20260520-327791-20200 Pack10，Linux。文中的输出都是原样贴的，实例端口不是默认的，为便于复制统一写成 5236。安全版另有 SYSSSO 账户、分权更细，本文没在安全版复跑，涉及处标「未实测」。

三十秒版本。用 SYSAUDITOR 登录，把下面 5 条粘进去，然后做一次操作，再换回 SYSAUDITOR 查记录。就这些。

-- 审计总开关
SP_SET_ENABLE_AUDIT(1);

-- 审计所有用户登录行为
SP_AUDIT_STMT('CONNECT', 'NULL', 'ALL');

-- 审计对表的 DDL
SP_AUDIT_STMT('TABLE', 'NULL', 'ALL');

-- 审计删除数据
SP_AUDIT_STMT('DELETE TABLE', 'NULL', 'ALL');

-- 审计修改数据
SP_AUDIT_STMT('UPDATE TABLE', 'NULL', 'ALL');

-- 审计查询表数据
SP_AUDIT_STMT('SELECT TABLE', 'NULL', 'ALL');

每条都返回 DMSQL executed successfully 就是配上了。查记录用同一账户（SYSAUDITOR）执行一句：

select username, operation, objname, succ_flag, sql_text, optime
  from sysauditor.v$auditrecords
 order by optime desc;

但这 5 条没有覆盖插入。要连 insert 一起记，得自己补一条 SP_AUDIT_STMT('INSERT TABLE', 'NULL', 'ALL');。为什么它值得单拎出来说，见「它记不到什么」。

先解决登录：审计员的密码，可能和管理员是同一个

SYSAUDITOR 是达梦内置的审计管理员账户，跟 SYSDBA 分权：开关、配规则、看记录都得用它，SYSDBA 反而看不了记录。

它没有默认口令。dminit 里 SYSAUDITOR_PWD 是必填项（实测 dminit help 标的是 REQUIRED，默认值 NOTHING），口令在建库那一刻由人填进去。

但现场十有八九两个口令是一样的。原因很朴素：装库的人不想多记一个密码，就把审计员口令填成了和管理员一样的。我这台实例正是这么来的——装库用的那套自研脚本（不是达梦官方安装程序）发现 SYSAUDITOR_PWD 留空，顺手拿 SYSDBA 的口令顶上，只留了一条告警：

[warn] SYSAUDITOR_PWD 留空，已沿用 SYSDBA_PWD
（影响：审计账号与管理员同口令将失去审计独立性
 处置：装完 alter user SYSAUDITOR identified by "<独立口令>" 分设）

还要澄清一句：SYSDBA 这个字符串，永远不可能是它自己的口令。达梦有硬校验，实测：

SQL> alter user SYSDBA identified by "SYSDBA";
[-2160]:Error in line: 1
Password must be different from login name.

建用户同理，create user audit_test_user identified by "audit_test_user"; 报同一条 -2160。反过来，口令里带 SYSDBA 字样是允许的（Sysdba1234 实测建用户成功），只要不等于用户名、且过得去复杂度校验——这台 PWD_POLICY=15，要求长度不小于 9、含大小写和数字。所以「口令恰好是 SYSDBA」这种说法从原理上就不成立。

现场真实发生的是：图省事的人把审计员口令填成了和管理员一模一样的那个字符串。一样，但不是「SYSDBA」这个词。这两件事在测评现场分量不同：后者改一下就好。

最快的判断办法：拿登录 SYSDBA 的口令直接试一次 SYSAUDITOR（下面这行的 SYSDBA的口令 换成你登录 SYSDBA 时敲的那串），能进就说明当初填的一样：

./disql SYSAUDITOR/SYSDBA的口令@127.0.0.1:5236
Server[127.0.0.1:5236]:mode is normal, state is open
login used time : 2.638(ms)

SQL> select user as who from dual;
LINEID     WHO
---------- ----------
1          SYSAUDITOR

这件事测评是要问的。审计员和管理员一个口令，等于三权分立没落地——管库的人能登审计账号，日志谁都能动。

分设口令有个反直觉的地方：SYSDBA 改不了审计员的口令，实测报：

SQL> alter user SYSAUDITOR identified by "Auditor_2026";
[-5549]:No alter user privilege.

得让审计员自己改自己，用新口令登录后再执行同一条语句，就成功了：

SQL> alter user SYSAUDITOR identified by "Auditor_2026";
DMSQL executed successfully

改完立刻验两件事：新口令能登；旧口令必须登不上。旧口令失败的样子有点误导——disql 不会直接说口令错，而是退回交互式让你重输，管道里没输入就连试三次退出去：

username:password:
[-70028]:Create SOCKET connection failure.
DISQL-10029: Can not connect to SERVER after three tries, exit DISQL

这个报错看着像网络断了。看到 -70028 先回头确认口令，别去查防火墙。我在这上面绕过一次弯。

口令忘了怎么办：用操作系统认证进去

DBA 交接、老项目接手、同事离职，最常见的就是「库还在跑，口令没人知道」。达梦有一条本地免密通道，前提是你能用装库的那个操作系统账号（一般是 dmdba）登到服务器上。

命令一行，三个地方不能省：

./disql /@127.0.0.1:5236 AS SYSDBA
  • 斜杠后面必须跟 @主机:端口。只写 / 会去连默认的 5236，实例端口不是 5236 时直接连不上——报出来的还是那句 [-70028] Create SOCKET connection failure，很容易误判成认证没开。
  • 必须带 AS SYSDBA。只写 /@主机:端口 不带身份，实测报 [-2501]:Invalid username or password.——它不是口令错，是达梦不知道该把你映射成谁（dmdba 不在 dmusers 组，库里也没有同名用户）。
  • 用 dmdba 执行，别用 root，原因见下面的边界表。

进去先看自己是谁（这张表就是实测输出）：

SQL> select user as who from dual;
LINEID     WHO
---------- ----------
1          SYSDBA

确认是 SYSDBA，口令就能直接改，不需要知道旧的：

SQL> alter user SYSDBA identified by "新口令";
DMSQL executed successfully

这条路我完整跑过一遍：改成临时口令 → 用新口令正常登录 → 再改回原口令 → 原口令验证通过。全程不停库。

它能进到什么程度，都是实测

试法结果
dmdba + AS SYSDBA成功，身份 SYSDBA
dmdba + AS AUTO成功，等同于 SYSDBA（自动匹配到有 DBA 权限的账户）
dmdba + AS SYSAUDITOR，未加组[-2512]:Unauthorized user . —— 默认进不去，补一个系统组就能进，见下一节
dmdba + AS SYSAUDITOR，已在 dmauditor 组成功，身份 SYSAUDITOR
root + AS SYSDBA[-2512]:Unauthorized user .
dmdba + AS DMDBA（普通用户名）不认，disql 直接打印用法
dmdba + AS SYSSSO连不上（企业版 SYSSSO 账户状态是 EXPIRED，安全版才有实际用途，本文未在安全版复跑）

两个结论。第一，只有装库的那个操作系统用户能用，root 也不行，这算一道天然的门。第二，AS 后面不是随便写谁就是谁，得对应到系统组或内置账户；不过审计员这条路是通的，只要补一个组——下一节。

安全上的话也得说一句：这条通道意味着谁能登 dmdba 系统账号，谁就是数据库管理员，跟知不知道口令无关。所以服务器账号管控、su 到 dmdba 的口令或密钥，就是最后一道门。测评问到「数据库账号安全」时，这一层也该一起答。

审计员也能免密：差别只在一个系统组

我一开始把上面那条 -2512 读成了「审计员没有 OS 认证通道」，这个判断是错的。达梦判断的不是用户名，是操作系统组：

操作系统组对应数据库账户默认有没有
dmdbaSYSDBA装库时就有（dmdba 用户已在该组）
dmauditorSYSAUDITOR没有，要自己建
dmssoSYSSO安全版用，企业版账户是 EXPIRED
dmusers与 OS 用户同名的数据库用户没有；同名用户那条路本文没跑通，标未实测

所以 SYSDBA 那条路天然通、SYSAUDITOR 天然 -2512。补上组就行，不用改参数、不用重启数据库：

groupadd dmauditor
usermod -a -G dmauditor dmdba
id dmdba        # groups 里要看到 dmauditor
su - dmdba
cd /home/dmdba/dmdbms/bin
./disql /@127.0.0.1:5236 AS SYSAUDITOR

进去之后身份和权限都是真的，不是「进去了但什么都干不了」：

SQL> select user as who from dual;
LINEID     WHO
---------- ----------
1          SYSAUDITOR

SQL> select count(*) as records from sysauditor.v$auditrecords;
LINEID     RECORDS
---------- --------------------
1          308

判据就是这个组，不含糊：把 dmdba 从组里删掉（gpasswd -d dmdba dmauditor），下一次连立刻回到 -2512；加回去，下一次连又通。整个过程没重启库、没重新登录系统账号。

审计员忘口令，用这条路三步救回来

走 OS 认证进来，会话身份就是 SYSAUDITOR 本身，所以「改自己口令」这条语句它有权限——正是 SYSDBA 执行时报 -5549 的那条：

-- 1. OS 认证进来，先改成临时口令
alter user SYSAUDITOR identified by "Temp12345";

-- 2. 退出，用临时口令正常登录，确认通

-- 3. 再走一次 OS 认证，改回正式口令
alter user SYSAUDITOR identified by "正式口令";

我完整跑过：改临时口令 → 密码登录成功 → OS 认证改回原口令 → 原口令验证通过。不停库、不需要旧口令，也不用 SYSDBA 帮忙。前提只有一个：ENABLE_LOCAL_OSAUTH=1（这台实例是 1），为 0 时先按下一节改回来。

顺手撞见的一条权限边界

拿到审计员身份后我多试了一步：SYSAUDITOR 能 create user，也能删自己建的用户；但 SYSDBA 删不掉审计员建的用户：

SQL> drop user t_by_auditor;        -- 用 SYSDBA 执行
[-5533]:Error in line: 1
No drop user privilege.

反方向一样：审计员删 SYSDBA 建的用户，同样报 -5533；而各自删自己建的都成功。原因不是"管理员权限不够"：SYSDBA 的系统权限只有 SELECT ANY TABLE、EXECUTE ANY PROCEDURE、SELECT ANY SEQUENCE、EXECUTE ANY PACKAGE、CREATE SESSION 五项，建/删用户靠 DBA 角色（CREATE USER / ALTER USER / DROP USER 都在这个角色里）；SYSAUDITOR 靠 DB_AUDIT_ADMIN 角色，同样带这三个权限。真正卡住的是：达梦压根没有 DROP ANY USER 这种跨属主权限——我把全部 DROP% 权限拉了一遍，只有 DROP USER，没有 ANY 版本。结论很实用：别拿审计员账号去建业务用户，建出来的账户 SYSDBA 收拾不了，只能再登审计员删。

它靠哪个参数：我关不掉

相关的是两个参数。这台实例的值实测如下，两个都不在 dm.ini 里（ENABLE_LOCAL_OSAUTH 的 file_value 显示 1，可是全文搜不到这一项，这个矛盾我还没查清，所以改它时一律以 v$dm_ini 为准）：

参数这台管什么
ENABLE_LOCAL_OSAUTH1本地操作系统认证。官方文档写的缺省是 0，所以每台装完先查一次；为 0 时上面所有 AS 写法都报 -2512
ENABLE_REMOTE_OSAUTH0远程操作系统认证，默认关（所以只能在本机免密）。远程还要配 ENABLE_ENCRYPT=1 走 SSL，本文未实测

查一行就够：

select para_name, para_value, file_value from v$dm_ini
 where para_name = 'ENABLE_LOCAL_OSAUTH';

如果是 0，开通两步，静态参数必须重启：

SP_SET_PARA_VALUE(2, 'ENABLE_LOCAL_OSAUTH', 1);

想把它关掉，我没有成功，过程如实记下：

  • alter system set 'ENABLE_LOCAL_OSAUTH' = 0 both; 报 [-839]:Try to alter static ini parameter.，静态参数不让动态改。
  • 停库，手工在 dm.ini 里加 ENABLE_LOCAL_OSAUTH = 0，重启后查 v$dm_ini，值仍然是 1。插在文件中间和追加在末尾都试过，一样。

所以「关掉这个参数就安全了」这句话我不敢写，这里标未实测。反过来提醒一句：如果你在测评答疑时说「我们已经关了 OS 认证」，最好先当场查一次值，别把没生效的改动说成已完成。

这 5 条各管什么

一条总开关，一条登录，三条数据操作。TABLE 那条最容易误读：它管的是表这个对象的 DDL（建表、改表、删表），不是表里的数据。表里的增删改查是另外四个类型，而素材里只给了三个。

命令记什么不记什么
SP_SET_ENABLE_AUDIT(1)打开审计总开关。关着的时候配规则，一条都落不下去不管具体记什么，得配合下面几条
'CONNECT'登录（LOGIN）、退出（LOGOUT）——
'TABLE'建表 CREATE TABLE、改表、删表表里的数据变化
'SELECT TABLE'查表数据count(*) 这类聚合，见下一节
'UPDATE TABLE'改数据——
'DELETE TABLE'删数据——

配完这 5 条，我建了一张测试表、插了一行、改了一行、查了一次、删了一行，记录原样长这样：

做的操作OPERATIONOBJNAMESQL_TEXT
登录CONNECTNULLLOGIN
建表CREATE TABLENULLcreate table SYSDBA.T_AUDIT_PROBE2(id int, v varchar(20));
插数据INSERTT_AUDIT_PROBE2insert into ... values(9, 'insert-probe');
改数据UPDATET_AUDIT_PROBE2update SYSDBA.T_AUDIT_PROBE2 set v = 'c' where id = 2;
查数据SELECTT_AUDIT_PROBE2select id, v from SYSDBA.T_AUDIT_PROBE2;
删数据DELETET_AUDIT_PROBE2delete from SYSDBA.T_AUDIT_PROBE2 where id = 1;
退出登录DISCONNECTNULLLOGOUT

几个细节：SQL_TEXT 是原样语句，口令会自动打码成 ******，明文不进审计表；DDL 的 OBJNAME 是 NULL，因为记录时对象还不存在；查审计视图这个动作本身也会留下一条 SELECT，OBJNAME 是 V$AUDITRECORDS——别把这行当成别人在翻你的业务表。

登录和退出不用单独配 DISCONNECT，配了反而报错：达梦没有这个类型，但 LOGOUT 照样会被记下来。

它记不到什么

这一节是重点。以下每一条都在同一台实例上验过，不是推测。

1. 素材里没有 INSERT TABLE，插数据就是查不到

先把 5 条配齐、插入一行，去查记录——只有 CONNECT 和 DISCONNECT 两条，INSERT 没有。补上这条命令之后再插一行，记录立刻出现：

SP_AUDIT_STMT('INSERT TABLE', 'NULL', 'ALL');
SYSDBA  INSERT  T_AUDIT_PROBE2  insert into SYSDBA.T_AUDIT_PROBE2 values(9, 'insert-probe');

所以「数据操作」这一组是四个类型，不是三个。只抄素材那三条，改和删都有记录、唯独看不出来谁插了数据——而测评最常问的恰恰是「谁改了这条数据」。

2. count(*) 这种聚合查询不留 SELECT 记录

同一张表，两种查法，结果不一样。空表上 select *，留痕；有 4 行数据的表上 select count(*)，没有留痕。

-- 有记录
select * from SYSDBA.T_AUDIT_EMPTY;

-- 没有记录
select count(*) as c from SYSDBA.T_AUDIT_PROBE2;

我一开始以为是「空表不记」，把两个变量拆开重测才发现反了：空表的 select * 记了，有数据的 count(*) 没记。是不是优化器跳过了表扫描，我没再往下查，但结论可以直接用：按 OPERATION='SELECT' 统计「谁查了这张表」，聚合类查询会漏。

3. 一条 update 会留两条记录，其中一条叫 SELECT

这是最容易误判的一条。执行一次改数据，记录里出现两行，SQL_TEXT 一模一样：

OPERATIONOBJNAMESQL_TEXT
SELECTT_AUDIT_PROBE2update SYSDBA.T_AUDIT_PROBE2 set v = 'c' where id = 2;
UPDATET_AUDIT_PROBE2update SYSDBA.T_AUDIT_PROBE2 set v = 'c' where id = 2;

删数据同理，也会多一条 SELECT。原因应该跟修改语句内部的按条件扫描有关，这层机制我没深挖，但影响很直接：记录条数会比你实际操作多一倍，做「操作次数」统计时不能按行数算；按 SELECT 追查「谁偷看了数据」时，也会把改数据的人算进去。

4. 删用户记成 EXECUTE，不是 DROP USER

如果按账户管理来配（USER 类型），删用户这条在记录里是：

OPERATIONOBJNAMESQL_TEXT
EXECUTESP_DROP_CONS_AND_OBJ_REFS_WHEN_DROP_SCHEMAdrop user T_AUDIT_U;

按 OPERATION='DROP USER' 过滤是查不到的，只能靠 SQL_TEXT 搜关键字。

5. SYSDBA 查不到记录，这是设计不是故障

SQL> select count(*) from sysauditor.v$auditrecords;
[-5504]:No select privilege on object [SYSAUDITOR.V$AUDITRECORDS].

这个报错最容易被读成「没有审计日志」。审计记录归 SYSAUDITOR 所有，SYSDBA 看不到，这正是三权分立。

顺带一个现场问到的点：V$AUDITRECORDS 是 17 个字段，除了上面用到的，还有 IP（客户端地址）、SCHNAME、SUCC_FLAG（成功 Y / 失败 N）、MAC、SEQNO、BIND_INFO（绑定变量）。列名是 SCHNAME 和 DESCRIPTION，写成 SCHEMANAME、DESCRIBTION 会直接报无效列名。

怎么确认规则真的在

我试过最自然的那个办法：select * from sysauditor.vsysauditrules;——0 行。规则配上去了，这个视图照样是空的。拿它当判据会得出完全相反的结论。

可靠的判据是把同一条规则再配一次，看返回什么：

-- 已经配过
SQL> SP_AUDIT_STMT('TABLE', 'NULL', 'ALL');
[-5302]:Has defined this audit type.

-- 之前没配上（比如开关当时是关的），这一次才生效
DMSQL executed successfully

这个幂等报错比查任何视图都准。

还有几条边界，顺便测了：

  • 审计关着的时候配规则，报 [-5301]:Audit off or not support.，规则一条都落不下去。所以顺序不能反。
  • 关掉再打开，规则不丢。设 SP_SET_ENABLE_AUDIT(0) 再开回 1，配过的 TABLE 仍然返回 -5302。
  • 取消规则用 SP_NOAUDIT_STMT，参数写法跟配的时候一样。取消之后再配同一个类型会重新成功（不再报 -5302），这就是「确实删掉了」的判据。
  • 重启服务，开关和规则都还在。断电重启前后查 ENABLE_AUDIT，值都是 1；反过来先设 0 再重启，值就是 0 —— 说明这个开关是持久化的。但 dm.ini 里并没有 ENABLE_AUDIT 这一项（文件修改时间也没变），也就是说它不靠配置文件记。这一点在克隆库、换机器、重建实例时值得留意：别以为拷一份 dm.ini 就把审计配置带走了。

会占多少磁盘，能留多久

审计文件在实例目录下的 audit/ 里，名字形如 AUDIT_DMSERVER_<哈希>_2026-11-20-22-16-48.log。注意它跟 SQL 日志不在一个地方（SQL 日志在 dmdbms/log），别翻错目录。

实测一件反直觉的事：文件是预分配 100MB 的。我这边只写进去 164 条记录，文件已经是 104857600 字节整。所以规划磁盘要按 100MB × 文件数 算，按记录条数估会严重低估。

参数实测默认管什么
AUDIT_MAX_FILE_SIZE100单个审计文件上限，单位 MB
AUDIT_KEEP_DAYS0最少保留天数，0 = 不按天淘汰
AUDIT_SPACE_LIMIT0审计目录总空间上限（MB），0 = 不限
AUDIT_FILE_FULL_MODE3写满时：1 删旧文件 / 2 停止写入 / 3 两者结合
AUDIT_FLUSH_LEVEL1刷盘时机：0 按语句 / 1 按事务 / 2 延迟
AUDIT_IP_STYLE00 只记 IP / 1 记「IP(主机名)」

一条命令全查出来：

select para_name, para_value from v$dm_ini where para_name like '%AUDIT%' order by para_name;

交付时该改的是 AUDIT_KEEP_DAYS。默认 0 意味着没有任何保留承诺，而网络安全法第二十一条要求网络日志留存不少于六个月，测评会看这一项。把它设到 180，是一条能当场查给测评看的参数。改完的淘汰行为本文没有实测，动生产参数前先在测试库验一遍。

对着条款说

GB/T 22239-2019 的 8.1.4.3 是安全审计，四条要求跟上面的配置基本对得上：

  • a) 覆盖每个用户和重要安全事件 → 'ALL' 是对所有用户生效，别为了少记点数据配成指定用户。
  • b) 记录含日期时间、用户、事件类型、是否成功 → OPTIME / USERNAME / OPERATION / SUCC_FLAG 正好四列。
  • c) 定期备份、防止被删改 → 内置审计自己做不到，得配合文件权限和备份策略；这也是它的边界，下面说。
  • d) 保护审计进程，防止未经授权中断 → 别「测评的人走了就关掉」。按需开启、事后收敛可以，但收敛完仍要覆盖 a) 的范围；长期关着是硬伤。

还有一条容易被忽略：审计表的权限本身也要管。上面那个 [-5504] 恰好是这条的正面例子——只有审计员能读，管理员读不到。

FAQ

规则表 VSYSAUDITRULES 查出来是空的，到底配上了没有？

不能拿这个视图当判据。实测 0 行，但规则已经生效——建表、改数据、查数据全都记下来了。两个更可靠的办法：同一条规则再配一次看是否报 -5302；或者干脆做一次操作，去 V$AUDITRECORDS 里看有没有新行。

为什么「全配上了，建表还是没有日志」？

按可能性排，前三种都能自己排查：

  1. 用 SYSDBA 查记录被权限挡住，把「无权限」读成了「没记录」
  2. 配规则的时候审计开关还没开，命令报了 -5301 但没注意
  3. 图形化界面里勾的是对象级审计，只覆盖已存在的表，新建的表不在范围内

三条都排掉还没有，再回头确认规则类型写对了：建表是 'TABLE'，不是 'CREATE TABLE'（后者报 [-5313]:Invalid audit type.）。

第二个参数为什么必须写成 'NULL'？

这是函数签名要求的字符串，不是 SQL 的 NULL 值。写成不带引号的 NULL：

SQL> SP_AUDIT_STMT('SELECT TABLE', NULL, 'ALL');
[-6860]:Invalid parameter value in [SP_AUDIT_STMT].

前面要不要加 call？

加不加都行。实测 SP_SET_ENABLE_AUDIT(1); 和 call SP_SET_ENABLE_AUDIT(1); 都能执行成功。倒是别名要注意：SP_AUDIT_STMT 的反操作是 SP_NOAUDIT_STMT，取消某条规则用它，参数写法一模一样。

内置审计能替代审计设备吗？

不能。它没有集中归并、实时告警，也防不住有文件权限的人删改审计文件（这一条是 8.1.4.3 c) 的要求，得靠外部措施补）。如果测评项里明确是采购「数据库审计系统」，那是另一件事。内置审计解决的是「数据库自己有没有记录、能不能查」，这也是最常见的那一问。

安全版呢？

企业版是 SYSAUDITOR 一个账户。安全版有 SYSSSO，账户形态和权限划分都不一样，本文没有在安全版复跑，命令不敢保证一字不差。

这篇不适合谁

要一键脚本、不想知道原理的：这篇给了命令，但也花了很大篇幅讲「它记不到什么」，那部分你现在可以跳过，等查不到记录时再回来。要过的是独立审计产品采购项的，也不在范围内。

卡在某一步了？

把卡在第几步、报错原文、select id_code from v$instance; 的输出这三样发我，够判断了。不用发审计记录内容，那里面有账号和 SQL 原文。
