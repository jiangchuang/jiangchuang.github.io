达梦开通信加密，不用配证书：改一个参数，重启，验证

日常运维

三十秒版本。用 SYSDBA 登录，改一个参数，重启服务，再查一眼取值。三步：

-- 第一步：改参数（只写进配置文件，重启才生效）
ALTER SYSTEM SET 'ENABLE_ENCRYPT' = 4 SPFILE;
# 第二步：重启服务，服务名按你机器上的实际名字替换
systemctl restart DmServiceDMSERVER
-- 第三步：确认内存里的值已经是 4
select para_name, para_value from v$dm_ini where para_name = 'ENABLE_ENCRYPT';

全程不需要生成 CA、不需要签发证书、不需要给每个用户配证书目录。应用侧的连接串也不用改。

如果连不上、或者库起不来，把同样的位置改回 0 再重启一次就恢复原状，回滚步骤见「出问题了怎么回滚」一节。

本文的输出来自一台 CentOS 7 单机 DM8（服务端构建号 03134284552-20260414-322369-20221，MIN_SSL_VERSION 默认 771 即 TLSv1.2），JDBC 用 DmJdbcDriver8.jar 8.1.4.200 验证。主备、DSC 这类多节点环境每个节点都要改，本文的多节点部分未实测。

测评问的是「有没有明文」，不是「证书链完不完整」

等保测评到数据库这一项，通常会问一句：客户端和数据库之间的传输加密了吗。

默认情况下，答案是「没有」。DM8 的 ENABLE_ENCRYPT 出厂值是 0，SQL 语句在网络上就是明文。我在测试机上抓过一次，一条 select 的完整文本连引号都在包里躺着，一眼就能读出来。

要加密，达梦给了几个档位。大家一般先查到的是一档，也就是 ENABLE_ENCRYPT=1，但那一档要证书：生成 CA、签服务端证书、给每个数据库用户签客户端证书、部署到 server_ssl 和 client_ssl 目录，连接时还要带 SSL_PATH 和 SSL_PWD。证书有过期时间，换人、加用户都得重签，一个环节没对上，连接直接失败。

如果诉求只是「测评别看到明文」，那这些活可以全省掉。ENABLE_ENCRYPT=4 这一档就是给这个场景准备的：

0: 不加密，也不验证证书（默认值）
1: 加密，双方交换并验证对方证书
2: 不加密，但双方交换并验证对方证书
4: 加密，但双方都不验证证书
5: 加密，仅客户端验证服务端证书（较新版本才有）
6: 商密 TLCP 认证与加密

4 这一档下面这行注释写得很直白，就在 dm.ini 里：

ENABLE_ENCRYPT = 4  #Encrypt Mode For Communication, ... 4: Only SSL Encryption

它用的是服务端自带的一张自签名证书。这张证书跟着安装包来，你不用生成，也不用管它什么时候过期，因为客户端压根不验证它。所以准确说法是「不需要你配证书」，而不是「握手时没有证书」。测评老师如果追问证书哪来的，答案就是这一句。

代价也要说清楚：不验证证书，就防不了中间人冒充服务端。它能挡住的是「同网段抓包直接读到 SQL」，挡不住「有人在你和目标库之间架一台假服务器」。内网过测评、防的是前者，这就够用。如果哪天要求防中间人，再升级到 1 或 5，参数改一下的事。

第一步：改参数

这个参数只有 DBA 能改，用 SYSDBA 登录就行。达梦装完默认口令也是 SYSDBA，如果你改过，换成自己的。

cd /home/dmdba/dmdbms/bin
./disql SYSDBA/SYSDBA@127.0.0.1:5236

进去以后执行这一句：

ALTER SYSTEM SET 'ENABLE_ENCRYPT' = 4 SPFILE;
SQL> ALTER SYSTEM SET 'ENABLE_ENCRYPT' = 4 SPFILE;
DMSQL executed successfully
used time: 80.857(ms). Execute id is 1301.

看到 DMSQL executed successfully 就算改成功了。但此时去查参数值，还是原来的 0，这不是没改上，是 SPFILE 的含义：只写进配置文件，不动内存。我实测过一次，把 4 改成 0 之后立刻查，内存里仍然是 4，重启完才变 0。

如果你不喜欢敲 SQL，也可以直接编辑配置文件。库停掉以后，打开 dm.ini，找到这一行改成 4：

ENABLE_ENCRYPT = 4                     #Encrypt Mode For Communication

这两种做法的结果一样，都是改文件。改完都必须重启，没有第二条路。这个参数是静态的，达梦不会热加载。

还有一条容易踩的：SPFILE 换成了 MEMORY 会变成「只改内存」，当时查着是 4，下次重启就回到 0，人走了才出问题。所以命令里那个 SPFILE 别省。

第二步：重启服务

小白最容易卡在这一步，因为「重启数据库」这句话在不同安装方式下长得完全不一样。先花十秒确认你的库是怎么起的，再选对应的那条。

先找服务名

达梦的服务名是安装时定的，一般是 DmService 加上实例名，但实例名不一定叫 DMSERVER。查一下就知道：

systemctl list-units --type=service --all | grep -i DmService
  DmServiceDMSERVER.service   loaded    active   running   DM Instance Service(DmServiceDMSERVER).

冒号前面那个带 .service 的就是你要的名字，用的时候可以省略后缀。下面统一写成 DmServiceDMSERVER，你换成自己查到的。

情况一：注册成了系统服务（最常见）

systemctl restart DmServiceDMSERVER

这条命令没有任何输出是正常的。确认起没起来：

systemctl status DmServiceDMSERVER --no-pager
● DmServiceDMSERVER.service - DM Instance Service(DmServiceDMSERVER).
   Loaded: loaded (/usr/lib/systemd/system/DmServiceDMSERVER.service; enabled; vendor preset: disabled)
   Active: active (running) since Fri 2026-11-20 10:20:45 CST; 22s ago
 Main PID: 2475 (dmserver)
   CGroup: /system.slice/DmServiceDMSERVER.service
           └─2475 /home/dmdba/dmdbms/bin/dmserver path=/dmdata/DAMENG/dm.ini -noconsole

看到 active (running) 和有 dmserver 主进程，就是起来了。再补一眼端口，5236 在监听才算真的对外服务：

ss -lntp | grep 5236
LISTEN  0  128  [::]:5236  [::]:*  users:(("dmserver",pid=2475,fd=3))

情况二：机器上没有 systemd 服务，但有服务脚本

达梦每个实例都会在 bin 下生成一个同名脚本，参数和 systemd 那套一样：

/home/dmdba/dmdbms/bin/DmServiceDMSERVER restart

脚本会打印启动过程，最后出现 SYSTEM IS READY 就是好了。

情况三：手动起的进程，没注册过服务

临时环境、测试机、或者当初用 ./dmserver 直接拉起来的库，属于这种。先找到进程：

ps -ef | grep dmserver | grep -v grep
dmdba  2475  1  0 10:20 ?  00:00:12 /home/dmdba/dmdbms/bin/dmserver path=/dmdata/DAMENG/dm.ini -noconsole

第二列是进程号，杀掉再重新拉起，注意换成你自己的库路径：

kill 2475
sleep 10
su - dmdba -c 'nohup /home/dmdba/dmdbms/bin/dmserver /dmdata/DAMENG/dm.ini > /tmp/dm_start.log 2>&1 &'

然后看日志最后几行，出现 SYSTEM IS READY 就是起来了：

tail -5 /tmp/dm_start.log
nsvr_process_before_open begin.
nsvr_process_before_open success.
SYSTEM IS READY.

这种起法机器一重启就没了，正式环境建议还是注册成服务，注册命令在 $DM_HOME/script/root/dm_service_installer.sh。

情况四：Windows

Windows 上达梦同样注册成服务，名字也一样。这一节我没有实测，命令是通用的，你执行时留意报错原文：

net stop DmServiceDMSERVER
net start DmServiceDMSERVER

或者用图形界面：Win + R 输入 services.msc，找到 DmServiceDMSERVER，右键「重新启动」。达梦自己也带一个「DM 服务查看器」，在开始菜单里，能直接点停止和启动。

第三步：验证

重启完，先用 disql 连进去，确认能连上：

./disql SYSDBA/SYSDBA@127.0.0.1:5236
Server[127.0.0.1:5236]:mode is normal, state is open
login used time : 7.182(ms)

然后查参数，重点看 PARA_VALUE 是不是 4：

select para_name, para_value from v$dm_ini where para_name = 'ENABLE_ENCRYPT';
LINEID     PARA_NAME        PARA_VALUE
---------- ---------------- ----------
1          ENABLE_ENCRYPT   4

到这里服务端就完事了。应用侧不用动，连接串保持原样：

jdbc:dm://127.0.0.1:5236

我用 8.1.4.200 的驱动实测过，连接串里没加任何 SSL 相关参数，直接连上，查询正常返回。客户端不需要证书目录，也不需要 SSL_PATH。这是 4 这一档最省事的地方：改的是服务端，客户端零改动。

如果应用用了连接池，记得重启应用。数据库重启那一刻所有连接都断了，连接池会自己重连，但有些池配置了较长的重试间隔，看起来像「改完更慢了」，其实是还在重连。

出问题了怎么回滚

动手之前先把退路想清楚。回滚就是把参数改回 0，但「怎么改」分两种：库还能连上，一条 SQL；库起不来，SQL 执行不了，只能直接动文件。

什么时候该回滚

三个信号，碰到任何一个都先回滚、再排查：

  • 应用连不上，报错里带 SSL 或者握手字样。多半是客户端驱动太老，不认识 TLS。
  • 重启后 SYSTEM IS READY 一直不出现，服务起不来。
  • 测评做完了要恢复原状，或者有第三方系统还在用改不动的老客户端。

回滚不动数据，这个参数只管连接通道，改了不会丢东西。所以判断标准很简单：加密这件事已经挡住业务了，就先回 0 把业务恢复，别在现场研究 TLS 版本。

情况一：库能连上，一条 SQL 加一次重启

alter system set 'ENABLE_ENCRYPT' = 0 spfile;

SPFILE 不能写成 MEMORY。这是静态参数，写内存不生效，重启之后还会被文件里的 4 顶回去。改完按第二步用过的那种方式重启一次：systemctl restart、服务脚本、或者 kill 掉进程重起，哪个顺手用哪个。

重启完验证两件事，值和连通，一次查完：

[B] SQL 改 SPFILE=0（不重启）
SQL> DMSQL executed successfully
  dm.ini: ENABLE_ENCRYPT = 0
  内存值: 4
[C] 重启服务
  服务状态: active
  内存值: 0
[D] 连通性
login used time : 3.954(ms)
1          ROLLBACK_OK

和开启时一模一样：文件改了、内存没动，重启才生效。回滚没有「立刻恢复」的捷径，这一次重启躲不掉。

情况二：库起不来，SQL 也执行不了

这种时候没有会话可用，只能直接改 dm.ini。Linux 上四步，一条 sed 就够，不用打开编辑器：

# 1 先停服务，别让它一边拉起来一边被你改文件
systemctl stop DmServiceDMSERVER

# 2 备份，改错了能退回（路径按你实际的 dm.ini 所在目录改）
cd /home/dmdba/dmdbms/data/DAMENG
cp dm.ini dm.ini.bak

# 3 只改 ENABLE_ENCRYPT 这一行，参数名写进表达式里，不会误伤别的行
sed -i 's/ENABLE_ENCRYPT *= *4/ENABLE_ENCRYPT = 0/' dm.ini
grep -n 'ENABLE_ENCRYPT' dm.ini

# 4 启动，然后按第三步验证
systemctl start DmServiceDMSERVER

那句 sed 是按「原来写的是 4」写的。如果你中途试过别的值（比如 5），把表达式里等号后面的 4 换成当前值就行，改完一定要用 grep 看一眼是不是真变成 0 了，别改完就重启。

grep 出来的那行长这样，值应该是 0，后面那一长串是原文件自带的注释，不用管：

613:		ENABLE_ENCRYPT                  = 0                     #Encrypt Mode For Communication, 0: Without Encryption; 1: SSL Encryption; 2: Only SSL Authentication; 3: GmSSL; 4: Only SSL Encryption

我把「停服务、改文件、再启动」这套走了一遍，库能起来，值是 0，登录正常：

[1] 停服务
  状态: inactive
  端口已释放
[3] 直接改文件 4 -> 0
613:		ENABLE_ENCRYPT                  = 0                     #Encrypt Mode For ...
[4] 启动服务
  状态: active
[5] 验证参数与连通
1          ENABLE_ENCRYPT 0
1          FILE_EDIT_OK

Windows 上同理：服务管理器里把达梦服务停掉，用记事本打开 dm.ini，找到 ENABLE_ENCRYPT 那一行把 4 改成 0，保存，再启动服务。Windows 这一节我没实测，但动的是同一个文件的同一行，没有别的差别。

两个细节。一是先停服务再改文件，否则服务脚本可能在你改到一半时又把它拉起来。二是只盯着 ENABLE_ENCRYPT 这一行改，不要全局替换数字 4，这个文件里 4 到处都是。

回滚后应用侧要做什么

连接串不用改回去，因为开启时你就没动过它。要处理的是连接池：数据库重启那一刻连接全断了，池子会自己重连，但有的池重试间隔长，表面上像是「回滚了还是慢」。把应用重启一次最干脆。

一个实测的小意外

我试过把值填成 9（一个不存在的取值），库照样起得来，也没报参数非法（当时没细查它实际按哪个模式在跑）。所以别指望「填错了会报错」这层保护：改完一定按第三步查一次，看的是内存里的 PARA_VALUE，不是你以为写进去的那个数。

我在测试机上跑了一遍

为了让「必须重启」这句话有证据，我把整个来回走了一次，输出原样贴上来。先改 0，不重启：

[1] 初始值:
1          ENABLE_ENCRYPT 4
[2] 改 SPFILE=0，不重启:
SQL> DMSQL executed successfully
  内存值仍为: 1          ENABLE_ENCRYPT 4

执行成功，内存里还是 4。SPFILE 只写文件，这一点在这里看得很清楚。接着重启：

[3] systemctl restart 后:
  内存值: 1          ENABLE_ENCRYPT 0

值变成 0 了。systemctl restart 这一条命令确实把参数从文件带进了内存。再改回 4，再重启：

[4] 改回 SPFILE=4:
SQL> DMSQL executed successfully
[5] 再 restart 后:
  内存值: 1          ENABLE_ENCRYPT 4
[6] 连通性:
login used time : 7.182(ms)
1          CONN_OK
used time: 2.070(ms). Execute id is 801.

有一点要说明白，免得你到 bin 目录下一看觉得被骗了：server_ssl 和 client_ssl 这两个目录是安装包自带的，文件日期还是 2023 年，不是这次操作生成的。4 这一档握手用的就是 server_ssl/server-cert.pem，我把它和 openssl 握手拿到的证书对过指纹，同一个值：

openssl x509 -in server-cert.pem -noout -subject -fingerprint -dates
subject= /C=cn/ST=hubei/O=dameng/OU=developer/CN=server/emailAddress=server@demeng.com
SHA1 Fingerprint=3B:5A:80:51:AA:C0:62:70:6A:77:2F:E5:68:DB:B5:47:58:41:6E:D7
notBefore=Jan  1 00:00:00 2022 GMT
notAfter=Jan  1 00:00:00 2032 GMT

所以「不用配证书」的意思是不用你生成、不用你分发、不用你续期，不是说机器上没有证书文件。那张证书的有效期到 2032 年，而且 4 这一档客户端不验证它，所以你全程不用管它什么时候过期。

顺带说一句怎么证明它真的在加密

这一步测评时可能用得上，不需要抓包工具，机器上有 openssl 就行：

openssl s_client -connect 127.0.0.1:5236 -brief < /dev/null
CONNECTION ESTABLISHED
Protocol version: TLSv1.2
Ciphersuite: ECDHE-RSA-AES256-GCM-SHA384
Peer certificate: C = cn, ST = hubei, O = dameng, OU = developer, CN = server

能握上手、看到协议版本和加密套件，说明通道已经是 TLS。最后那行 Peer certificate 就是服务端自带的那张自签名证书，CN 是 server，签发者写的是 dameng。它同时会报一句 self signed certificate in certificate chain，这是预期的：4 这一档不验证证书，所以 DM 客户端不会因为这个报错，而 openssl 是照规矩提醒你一句。

要更硬一点的证据，就在数据库服务器上抓一次包，对比开关前后包里还有没有 select 的字样。我这边实测的结果是：改成 4 之前，一条 select 的完整文本在包里出现 4 次；改成 4 之后，同样一条语句 0 次，包里出现的是 TLS 记录。

FAQ

4 和 1 到底差在哪，测评能过吗

差在「验不验对方身份」。1 是加密加双向验证，要证书；4 是加密，双方都不验证，服务端用自带的证书完成握手。测评关注的是「传输是否加密、是否能看到明文」，4 能满足；如果测评问卷里明确写了「应采用证书进行身份认证」这类条款，那就得走 1 或 5。拿不准就把问卷那一条发我，我帮你对。

要不要先生成证书

不要。4 这一档不需要你生成、部署、更新任何证书文件。安装包自带 SSL 运行库，也自带 bin/server_ssl（一张 2023 年签发、2032 年到期的自签名证书）和按用户分目录的 bin/client_ssl，这些都用不着你动，客户端也不会拿它们做校验。

改完不重启，行不行

不行。ENABLE_ENCRYPT 是静态参数，只认重启。我实测过，SPFILE 改完查内存值还是旧的，重启才变。

应用要不要改连接串

不用。用 8.1.4.200 驱动实测，原始连接串直接连上，不加 SSL_PATH、不加 sslFilesPath。老驱动、其他语言的驱动未实测，如果连不上，报错里通常会提到 SSL 或握手，先换一个新一点的驱动试。

改完连不上了怎么办

先看报错。[-70019] 一类的通信错误、或者连接直接被断开，多半是客户端太老，不认识 TLS 握手。临时回退很干脆：把参数改回 0，重启一次，立刻恢复原状。完整步骤在「出问题了怎么回滚」那一节，库起不来、SQL 都执行不了的情况也写了。

服务端起不来了

如果重启后 SYSTEM IS READY 一直不出现，先看日志里有没有 SSL 相关的报错。精简安装（只装了 server 包、缺 SSL 运行库）的机器上会遇到。这种要么补装，要么先改回 0 把库起起来再排查。日志位置在 dm.ini 同目录下，或者用 select * from v$dm_ini where para_name = 'SVR_LOG' 看开关。

主备、DSC 这种多节点的怎么改

每个节点都要改，而且顺序有讲究：先改备机、重启备机，最后改主机。我这台是单机，多节点未实测，别照抄顺序，动手前先在测试环境走一遍。数据守护环境下 dmwatcher 会感知实例重启，可能触发一次切换，选低峰期做。

还有别的写法吗

有，sp_set_para_value(2, 'ENABLE_ENCRYPT', 4) 也能写进配置文件。这条我没实测，建议用上面那个 ALTER SYSTEM，输出明确，成功后有一行 DMSQL executed successfully，好确认。

改完要不要重新登录才能确认

不需要。重启之后新建立的连接就是加密的，直接 disql 连一次，查参数看值就够了。老连接在重启那一刻已经全断了，不存在「混合状态」。

最后

这个参数的价值不在于技术难度，在于它把「要不要上加密」从一道证书工程题，变成了一次改配置加一次重启。很多现场卡住不是因为不想加密，是因为没人愿意为了过一项测评去维护一套证书的生命周期。

要提醒的只有一句：4 挡的是窃听，不是冒充。知道自己在买什么，就不会在测评答辩时被问住。
