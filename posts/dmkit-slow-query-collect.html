文中每条命令、每个输出都是真机跑出来的，跑不了的地方标了「未实测」。三处视图用法和网上流传的写法不一致，我是实测之后才敢写——差异都列出来了，你可以自己复核。

你接到的求助，通常只有一句话

「这条 SQL 很慢，你给看看。」

然后就没了。没有 SQL 全文，没有执行计划，不知道表有多大，也不知道是一直这么慢还是今天突然慢。你在电话里问一句「执行计划能发我吗」，对面沉默三秒，回你「那是什么」。

远程连过去看一眼，卡得你想砸键盘；跑一趟现场，来回半天。于是这件事就悬在那儿——不是你不会调，是拿不到能调的料。

所以下面这套东西，解决的不是「怎么优化」，而是怎么用最低的代价，把判断瓶颈需要的那几样凑齐。凑齐之后，判断本身反而是快的。

为什么定位不了：信息量差了一个数量级

同样一句「慢」，不同信息量能推出的结论差很远：

你手上有的能判断出什么
「有个查询很慢」什么也判断不了
「这条 SQL 很慢」能猜，但猜不准
SQL 全文 + 执行计划 + 实测指标 + 表规模能指出瓶颈在第几步、该改什么

这四样里，最常被漏掉的是最后一样：表有多大。同一个执行计划，1 万行全扫是正常的，1 亿行全扫就是灾难。没有表规模，前面三样都可能被误读。

而这四样，恰好都能从库里取出来，不需要人肉问、不需要装客户端、不需要 SSH 登服务器。

先分清：哪些动作会真的跑一遍 SQL

讲命令之前先把边界摆出来，因为这里最容易出事。慢查询采集分两档，默认那一档不执行你的 SQL：

档位命令执行 SQL拿到什么
只读档（默认）at --file slow.sql不执行执行计划、涉及表、关键列索引、索引建议
完整档at --file slow.sql --run执行一遍上面全部 + 实测耗时 / 逻辑读 / 物理读

只读档走的是 EXPLAIN FOR：只让优化器给个计划，不取数据、不锁行、不触发函数副作用。生产库上午高峰我也敢跑它。

完整档必须真跑一次，才有真实耗时和逻辑读——这是它的价值，也是它的代价。这四类语句尤其要小心：大表全扫、SELECT ... FOR UPDATE（持锁）、含自定义函数（可能有副作用）、跨表 JOIN 大结果集。

判断标准很简单：这条 SQL 现在再跑一次，业务上允许吗？允许就 --run，犹豫就别加。

只读档到底能看到什么

这是真实输出，5 万行表、CODE 列无索引、查 WHERE CODE='CODE500'：

◆ 实测（⊘ 只读档 · 未执行原 SQL）
  无实测耗时/逻辑读/真实扫描行数——这些只有真跑一次才有。
  计划、涉及表、索引建议照常可用，判瓶颈通常够用。
  要真实指标：在命令末尾加 --run（原句执行一遍，慢 SQL 会花掉它真实的耗时）

◆ 计划（EXPLAIN FOR，关键行）
  4 #CSCN2 T_RO_TEST(INDEX33555503)  [全扫] 预估50,000

◆ 涉及表与关键列索引
  T_RO_TEST（行数未知：未收集统计；dmkit stat --table T_RO_TEST 可补）
    CODE     VARCHAR        无索引 ←

◆ 索引建议（依据自行取舍；批量复核用 dmkit ix）
  ✗ T_RO_TEST(CODE)  ←  预估全表扫描 50,000 行（ROW_NUMS）
  CREATE INDEX IDX_T_RO_TEST_CODE ON "SYSDBA"."T_RO_TEST" ("CODE");

加 --run 之后，只多出这一行：

◆ 实测（真实执行）
  耗时 6ms ｜ 逻辑读 72 ｜ 物理读 0 ｜ 返回 1 行 ｜ SQL_ID 219

所以取舍很清楚：判「瓶颈在第几步」用只读档就够；要「改完快了多少」的对比数据，才需要完整档。

顺带解释两个容易看错的地方：

「行数未知」不是表空，是这张表还没收集过统计信息。USER_TABLES.NUM_ROWS 是空的，工具如实说未知，而不是编一个数给你。

[全扫] 却写「索引建议：无」，也不是矛盾——见后面那一节。

三处网上写法，实测对不上

采集这件事最怕照抄旧文章。下面三条是我在 DM8 真机上逐条验证的，都跟流传的写法有出入：

流传的写法实测结果
V$SESSION不存在，达梦是复数 V$SESSIONS，直接报 [-2106] 表或视图不存在
用 SQL_TEXT_ID 关联历史 SQL、计划、统计V$SQL_HISTORY 里没有这一列。跨视图的通用键是数字 SQL_ID
用 V$SQL_STAT 查历史慢 SQL它只保留当前缓存里的少量语句，我这台实测只有 4 行。查历史必须用 V$SQL_HISTORY

另一个流传很广的说法是「SQL 全文只有 dmsql 日志里才有，视图里会被截到 1000 字符」。这条也站不住：V$SQLTEXT 存的是全文。我造了一条 1333 字符的语句跑进去，查出来 LENGTH(SQL_TEXT) = 1332，没截断。

但截断确实存在，只是在别的地方：V$PLN_HISTORY.TOP_SQL_TEXT 是截断的。所以正确姿势是——从 V$SQL_HISTORY 拿到慢 SQL 的 SQL_ID，再用它去 V$SQLTEXT 取全文，而不是从计划的 TOP_SQL_TEXT 里凑。

-- 1. 谁最慢（按累计耗时和逻辑读一起看）
select sql_id, time_used, n_logic_read, substr(top_sql_text,1,80)
  from v$sql_history
 order by time_used desc
 limit 20;

-- 2. 拿全文（这一步不会被截断）
select sql_id, sql_text from v$sqltext where sql_id = '上一步的ID';

-- 3. 拿执行计划
select sql_id, sql_plan from v$pln_history where sql_id = '上一步的ID';

上面这三条只是把链路讲清楚。日常不用手敲，一条 dmkit at 就把这三步连同索引情况一起做完了。

三条铁律，不遵守会白忙

这三条都来自真实翻车，不是凑数。

第一：SQL 一律走文件，别写在命令行里

达梦的动态视图名和列名里带 $ 的一堆：V$SQL_HISTORY、V$SESSIONS、STATUS$。在 PowerShell 里用双引号包 SQL，$SQL_HISTORY 会被当成变量替换成空。

你在 PowerShell 里敲的实际传给程序的结果
--sql 'SELECT 1 FROM V$SQL_HISTORY'SELECT 1 FROM V$SQL_HISTORY✅
--sql "SELECT 1 FROM V$SQL_HISTORY"SELECT 1 FROM V❌ $SQL_HISTORY 被吃掉

阴险的地方在于报错：它会告诉你「表或视图不存在」，于是你以为库有问题，其实命令早就残了。所以规矩定死——SQL 存成 slow.sql（UTF-8），用 --file。文件里写什么就收到什么，cmd / PowerShell / Linux 全都不打架。

顺带说一句，cmd 不认单引号。要发命令给同事，别默认对方和你用的是同一个 shell。

第二：DSN 用单引号

dm://SYSDBA@192.0.2.10:5236 这种串本身不带 $，但它经常跟别的东西拼在一起传。统一用单引号，少一类事故。

第三：尽量用一个 DBA 只读账号

普通账号能拿到执行计划和表结构，但拿不到 V$SQL_HISTORY 里的逻辑读，等于少了一半证据。而且不是「少一点」——实测业务账号查 V$SQL_HISTORY 直接报 -5504 无权限，一条都拿不到。工具遇到权限不足会自动降级并如实提示，不会假装采到了——但你最好别让它降级。

拿到执行计划之后，按这个顺序看

计划里能出问题的方向就五个。顺序有讲究：先改天花板，再看放大系数，最后才怀疑统计。顺序错了会白折腾几小时——比如先去收统计，结果发现瓶颈是缺索引。

序计划里的信号说明动作
①CSCN2 全表扫 + 行数巨大没索引，在读全表建索引
②有索引但仍 CSCN2谓词写法让索引用不上（列上函数 / 隐式转换 / LIKE '%x'）改写谓词
③NL 方向反 / 多余物化驱动表选错调连接顺序 / 换 HASH
④预估行数 vs 实际差一个数量级统计信息过期收统计（先验证逻辑读是否真降）
⑤计划正常但仍慢锁等待 / 高水位 / 资源竞争查锁、查资源

为什么 ① 在 ② 前面？因为「读多少行」由谓词和访问路径决定，「怎么读」才轮到索引和连接方式。先堵最大的漏，再看放大。

两条实测结论，省你两天

这两条都是同一个案例上跑出来的：一条前缀匹配的慢查询，测试环境复现，5921 ms。

一、收统计不是万能药。从「无统计」收到「精确」，耗时 5921 → 5894 ms，只降了 0.5%，逻辑读 15,596,271 一点没动。收统计只解决「估算错」，不解决「该读的数据本来就多」。

二、谓词改写才是大头。同一句，把 LIKE CONCAT(前缀,'%') 改成 SUBSTR(CODE,1,4)=前缀，耗时 5921 → 462 ms（-92%），逻辑读降了 98.7%。

一句话记：「读多少」由谓词决定，「怎么读」由索引决定——先改谓词，再谈索引。

补一句边界：SUBSTR(CODE,1,4)=... 这种改写的前提是前缀长度固定，能写成常数。变长前缀就回到原来的问题，别硬套。

一个反直觉的坑：全表扫，却告诉你「不用建索引」

这个我是拿一张 30 万行、CODE 列没索引的表测出来的，第一版就翻了车。

计划里明明是 CSCN2 全扫 30 万行，工具结尾却写「索引建议：无（未发现达阈值的全表扫描，或现有索引已覆盖）」。前后矛盾，而且误导性极强——客户会以为「数据库说不用建索引」。

原因是达梦全表扫的时候，计划节点上的 IDX_NAME 不是空，而是填了表自带的聚集索引名，形如 INDEX33568143。判「是否全扫」的逻辑如果要求「索引列为空」才算全扫，就会把全扫认成走索引，于是建议被吞掉。

修完之后，同一个场景正常给出：

◆ 索引建议（依据自行取舍；批量复核用 dmkit ix）
  ✗ T_SLOW_TEST(CODE)  ←  预估全表扫描 300,000 行（ROW_NUMS）
  CREATE INDEX IDX_T_SLOW_TEST_CODE ON "SYSDBA"."T_SLOW_TEST" ("CODE");

写这件事不是为了说工具多靠谱，反过来——这类「看起来正常、结论反了」的显示，比直接报错危险得多。报错你会去查，温和的错误结论你会直接拿去用。所以工具给的建议只当参考，CREATE INDEX 只打印不执行，落库前你自己判断：会不会拖慢写入、跟现有索引重不重复。

还有一种情况工具会故意不给建议：谓词上套了函数（SUBSTR(col,1,4)=...、NVL(...)、col+1）。这时候普通索引天然用不上，硬给一个 CREATE INDEX 是害人，正确动作是改写谓词或建函数索引。所以它会在结论下面补两行说明为什么这里给不出普通索引建议——看到「索引建议：无」时别只看那一句，下面那两行的解释才是重点。

什么时候需要更重的采集

只读档 + 完整档解决八成问题。剩下两成，是需要别人在你不在场时也能重建现场的：

场景用什么
快档看不出原因、要交给专家深挖qopt：8 段完整病历（环境与参数、DDL、统计、预估 vs 实际、10053 判读、复现指引）
怀疑优化器选错计划，想看它怎么想的qopt --with-10053，把决策过程翻成人话
手上有 dmsqlq 导出的 top SQL 清单ix 批量扫，找漏建索引的
要留证据、事后复盘dump 把周边环境一起打包

两个坑先说在前面：

--with-10053 依赖一个 UTL_FILE 目录对象 PLN_TRC，首次使用要先跑一次 qopt --setup-dir 把它建出来——这是库级写操作，需要 DBA 权限。不先建的话它只会告警、跳过这一段，不会偷偷替你建。

ix 的输入是 dmsqlq -o 导出的清单格式，不是随便一个 .sql 文件。而且它会逐条真实执行，清单里混着 UPDATE/DELETE 的话，先剔掉再喂。

发出去之前，四样东西建议处理掉

采集报告里必然带环境和业务痕迹。对外发之前过一遍：

  • 具体数据值（身份证、手机号、金额）→ 替换或删掉
  • IP、主机名、实例名 → 建议替换
  • 账号密码 → 永远不要发
  • 表名/字段名 → 不影响判断，可保留；涉及敏感业务就换成 T1/T2、C1/C2

这一条不是客套。报告里带着客户内网 IP 和库名发到群里，出事的是你。

常见问题

密码里有 @，DSN 怎么写？

不用转义，驱动按最后一个 @ 切分账号和主机。含 ? 结尾的补一个 ?；不要用 %40 这种 URL 编码。

只有普通账号，还能采吗？

能，但会降级：拿到执行计划、表结构、索引情况，拿不到逻辑读和真实耗时。工具会明确写「逻辑读/物理读未取到（需 DBA 类账号）」，不会给你 0 让你误以为是好事。

实测（DM8 默认配置，只有 RESOURCE 角色）：普通账号能查的只有 V$INSTANCE、V$VERSION、V$DATABASE，加上自己的 USER_TABLES/ALL_TABLES；V$SESSIONS、V$SQL_HISTORY、V$SQL_STAT、V$SQL_PLAN、DBA_TABLES 全部 -5504。也就是说，慢查询靠的视图一个都查不到。

确实只能用业务账号，让 DBA 加一条就够（不用给 DBA 角色）：

GRANT SELECT ANY DICTIONARY TO 你的账号名;

用完回收，撤完记得核一眼：

REVOKE SELECT ANY DICTIONARY FROM 你的账号名;
SELECT GRANTEE, PRIVILEGE FROM DBA_SYS_PRIVS WHERE GRANTEE='你的账号名';

授权和撤销都要重新连接才生效，已有连接还是旧权限。

表显示「行数未知」怎么办？

这张表没收集统计信息。补一条：dmkit stat --table T_RO_TEST。但注意——按前面第二条实测铁律，收统计未必能提速，它只让估算变准。

报「表或视图不存在」，是不是版本不兼容？

先看错误码，这两类完全不是一回事，处理方向相反：

错误码真实原因怎么改
-2106 Invalid table or view name表在别的模式、SQL 没写前缀；或视图名写错（达梦是 V$SESSIONS 复数，不是 V$SESSION）端口后带 ?schema=模式名，或 SQL 里写全 模式名.表名
-5504 No select privilege账号没权限，对象其实存在换 DBA 账号，或让 DBA 授 SELECT ANY DICTIONARY

顺带说一句：加 SET SCHEMA SYS 解决不了 -5504。达梦的报错里已经写明 [SYS.V$SQL_HISTORY]——它早就找到对象了，是在告诉你「你没权限」。切模式改的是名字往哪儿找，不是能不能看。

如果确实怀疑命令被打残（SQL 写在命令行、或用了双引号），先把 SQL 存文件重试一次；再查本机有哪些视图：

select view_name from all_views where view_name like 'V$SQL%' order by 1;

Mac 能用吗？

没有专门的二进制包。Intel Mac 可以试 Linux 版，不保证跑得起来；Apple 芯片跑不了。替代方案是拿一台 Windows 机器，或者直接在数据库所在的 Linux 服务器上跑。

能不能离线判读别人发来的文件？

能。qopt --trace-file xxx.trc 不连库，直接读 10053 跟踪文件。

最后

这套流程只解决一件事：把「很慢」变成一份能直接判断的东西，成本压到当事人十分钟内能做完。

它做不到的也说清楚：不替你判断这条 SQL 业务上该不该存在，不替你决定索引要不要建，也不保证每个结论都对——启发式规则不理解你的业务语义。它给你证据和优先级，判断还是人做。

用着有问题，或者你手上的库它采不出来，提个 issue，把命令原文、报错原文、dmkit version 的输出贴上就够定位。
