达梦怎么看逻辑读：三步拿到那个数字，然后让它变小

性能优化

三十秒版本。逻辑读 = 这条 SQL 读了多少个页（页大小按建库值，常见 8K）。它不像耗时那样一忙就飘，是你能自己量、自己比的那个数。三个入口：管理工具（选 SQL → 工具栏下拉选 TRACE → 执行）、命令行（set autotrace traceonly 加一句 SQL）、事后查（V$SQL_HISTORY）。

文中每个数字都是在一台 2G 内存的单机 DM8 上跑出来的（Linux，Pack10，8K 页，30 万行表），不是抄的。三处和流传写法对不上的地方单独列了出来：达梦的逻辑读不含物理读、两个入口的数字天然对不上、explain 根本看不到逻辑读。

「你优化一下这个查询」

这句话接下来怎么接，取决于你手上有什么。

如果你只有一个耗时，那就很被动：同一条 SQL，机器闲的时候 200 毫秒，隔壁跑个报表就变成 3 秒。你改完了再跑一次，快了，可你不知道是自己改对了，还是这会儿机器不忙。拿着这种数据去跟人说「优化好了」，自己心里也没底。

逻辑读解决的就是这件事。它数的是这条 SQL 在内存里访问了多少个数据页，跟机器忙不忙、缓存热不热都没关系。同一个 SQL 改前改后各跑一次，数字从 4548 降到 11，这话是可以拿到会上说的。

所以下面先给能直接用的东西，怎么理解放到后面。赶时间的话，看到「拿到数字之后，只比三件事」就可以走了。

入口一：DM 管理工具，点四下

图形界面最省事，SQL 写在哪就在哪执行，不用记命令。

步做什么在哪
1选中要测的那条 SQLSQL 编辑区里用鼠标拉选中。不选，就执行整段
2点工具栏上那个下拉箭头「手动提交」右边那个，默认显示 INDEX
3选 TRACE 或 TRACEONLY下拉里有三项：INDEX、TRACE、TRACEONLY
4点执行跟平时执行一样，快捷键也行

两者的区别工具里写得很清楚：TRACE 会显示结果集，再加执行计划和监控信息；TRACEONLY 不显示结果集，只给计划和统计。只想看逻辑读，选 TRACEONLY，省得刷一屏数据。

执行完，下面「消息」窗口先是执行计划，再往下是 Statistics 面板。我在测试机上执行 select * from dual，出来是这样：

Statistics
----------------------------------------------------------
          0  data pages changed
          0  undo pages changed
         59  logical reads
          0  physical reads
          0  redo size
        146  bytes sent to client
         84  bytes received from client
          1  roundtrips to/from client
          0  sorts (memory)
          0  sorts (disk)
          0  rows processed
          0  io wait time(ms)
      2.473  exec time(ms)

盯住 logical reads 这一行就行。连查一个 dual 都要 59 次，不是它读了一行数据，而是这个会话里第一次执行要先把解析结果和字典页摸一遍——同一条再执行第二次就归零了。所以这个数不要横向比，要纵向比：同一个 SQL 改前改后各跑一次。

顺带说一个总被问的字段：rows processed 对 SELECT 恒为 0，达梦在这一栏只记 DML 影响行数；返回了多少行看上面的 rows got（管理工具里看结果集）。

这个下拉默认停在 INDEX，很多人以为工具只能看执行计划，就是因为没点开过它。INDEX 只是把计划里的扫描方式标出来，不给统计。

说明一下边界：我的测试环境是 Linux 服务器，开不了这个客户端，所以上面四步是照界面写的；数字来自下一节命令行那条路，两边 Statistics 的字段和含义完全一致。

入口二：disql 里两行

没有图形工具，或者要连的库在服务器另一头，用命令行。打开 disql 连上库，先开统计开关，再执行 SQL：

set autotrace traceonly;
select * from SYSDBA.T_LR where code = 'CODE500';

输出是这样的（计划在上，统计在下）：

1   #NSET2: [8, 7500, 116]
2     #PRJT2: [8, 7500, 116]; exp_num(5), is_atom(FALSE); INFO_BITS(0)
3       #BLKUP2: [8, 7500, 116]; IDX_LR_CODE(T_LR); use_clu_addr(0)
4         #SSEK2: [8, 7500, 116]; scan_type(ASC), IDX_LR_CODE(T_LR), scan_range['CODE500','CODE500'], is_global(0)

300 rows got

Statistics
        -----------------------------------------------------------------
          0   data pages changed
          0   undo pages changed
        963   logical reads
          0   physical reads
          0   redo size
      37850   bytes sent to client
        169   bytes received from client
          2   roundtrips to/from client
          0   sorts (memory)
          0   sorts (disk)
          0   rows processed
      0.000   io wait time(ms)
      1.313   exec time(ms)

字段名和图形工具那一屏完全一致，logical reads 就是你要的那个数。rows got 是返回了 300 行，但这不是重点，重点是它读了 963 个页。

两种模式：

命令给结果集什么时候用
set autotrace traceonly;不给默认用这个。只想看数，不想刷屏
set autotrace on;给要顺手看一眼查出来什么
set autotrace off;关掉测完关掉，不然每条 SQL 都输出一坨

注意 traceonly 也是真执行，不是只看计划。大表上的 SQL 在生产库里跑，该慢还是慢，该锁还是锁。这一点跟 explain 完全不同，后面会讲。

入口三：事后查历史

SQL 已经跑完了、现场没了，或者你想看「这条 SQL 最近几次都花了多少」，查 V$SQL_HISTORY。逻辑读的列名叫 N_LOGIC_READ，注意不是 LOGIC_READS：

select * from (
  select sql_id,
         substr(top_sql_text, 1, 44) txt,
         n_logic_read, n_phy_read, time_used, start_time
    from v$sql_history
   where top_sql_text like '%T_LR%'
   order by start_time desc
) where rownum <= 8;

跑出来是这样（time_used 单位是微秒）：

SQL_ID  TXT                                         N_LOGIC_READ  N_PHY_READ  TIME_USED
------  ------------------------------------------  ------------  ----------  ---------
17      select count(*) from T_LR where code='CODE50            4           0         79
16      select * from T_LR where code='CODE500';                772           0        515
16      select * from T_LR where code='CODE500';                772           0        647
13      create index IDX_LR_CODE on T_LR(code);              19830        4033     530380

这个入口的好处是事后也能翻，不用提前开开关，也不影响正在跑的业务。坏处是它依赖历史记录留了多久，跑得太久远的可能已经被顶掉。

拿到数字之后，只比三件事

不要盯着绝对值问「多少算慢」，这个问题没有答案。看三个相对关系：

  1. 同一个 SQL，改之前和改之后。加了索引、改了写法，数字变小就是变好。这是最硬的证据。
  2. 全表扫的逻辑读，应该约等于这张表占了多少块。对得上，说明就是老老实实扫了一遍；对不上，说明计划或者统计有问题。查块数用 select blocks from user_segments where segment_name='T_LR';
  3. 别看耗时下结论。缓存一热，同一条 SQL 从 278 毫秒掉到 16 毫秒，逻辑读一个数都没变。

第三点值得单独说一句，因为它是最常见的自欺：你改完 SQL 再跑一遍，快了十倍，很满意。其实只是第二次执行，页都在内存里了。

下面开始拆解，不影响你用

从这里往后是「为什么」。上面那三条够你交差了，想搞明白再往下看。

逻辑读数的是页，不是行

一个页 8K，这是建库时定的，查一下就知道（PAGE 返回的是字节数，不是固定 8K：8K 页的库查出来是 8192，32K 页的库是 32768，按你库里查到的值换算）：

select page from v$database;
PAGE
----------
      8192

所以 logical reads = 4548 的意思是：这条 SQL 在内存里摸了 4548 个页，折合 36MB 左右。跟它返回了 101 行还是 3 行没关系。

我那张测试表 T_LR 灌了 30 万行，每行 116 字节，占多少：

select segment_name, blocks, bytes/1024/1024 mb
  from user_segments
 where segment_name in ('T_LR','IDX_LR_CODE');
SEGMENT_NAME  BLOCKS      MB
------------  ------  ------
IDX_LR_CODE      944       7
T_LR            4560      35

表 4560 块，全表扫的逻辑读 4548。对得上，这就是「扫了一遍」的样子。

一个实验：三条 SQL，4548 / 911 / 11

同一张表，同一个过滤条件，只换写法和索引，逻辑读差了 400 多倍：

SQL执行计划返回行逻辑读
select * from T_LR where id between 100 and 200CSCN2 全表扫1014548
select * from T_LR where code = 'CODE500'SSEK2 索引扫 + BLKUP2 回表300911
select code from T_LR where code = 'CODE500'SSEK2 只扫索引30011

第一个结果大概会让人愣一下：返回 101 行的花了 4548 次，返回 300 行的只花了 11 次。

因为第一个没索引，只能从头扫到尾，读完 4548 个页才挑出 101 行。第三个走索引，而且要的列就在索引里（索引建在 code 上，查的也是 code），不用回表去拿整行，扫了 11 个索引页就完事，300 行全在里面。

中间那个是常态：走索引找到位置，再回表取整行。code='CODE500' 命中 300 行，散落在 300 个不同的页上，于是回表就是 300 次页访问，加上索引页，九百多。

这就是为什么 select * 有时候比 select 几个字段 贵一个数量级，也是「覆盖索引」这个词的实际含义：要的列全在索引里，就不用回表。

为什么拿它当优化目标，而不是耗时

同一条全表扫的 SQL，连跑两次，我记录下来的是这样：

第几次逻辑读物理读耗时
重启后第一次5624028278 ms
第二次4540016 ms

耗时差了 17 倍，逻辑读基本是同一个量级（这两个数为什么不一样，下一节说）。你要是拿第一次的 278 毫秒当基线，改完再测 16 毫秒，会误以为自己优化了一个数量级，其实一行代码都没改。

逻辑读不受这个影响，所以它能当尺子。耗时也有用，但它说明的是「用户等了多久」，受服务器负载、缓存、网络一堆因素影响，不适合用来判断「这条 SQL 本身好不好」。

和 Oracle 不一样：达梦的逻辑读不含物理读

这条必须单独讲，因为它跟 Oracle 的经验是反的，而国内大部分教程是照着 Oracle 抄的。

Oracle 里，逻辑读是「访问缓冲区的总次数」，物理读是其中没命中、要去磁盘的那部分，所以逻辑读包含物理读。达梦不是。上面那张表里，冷缓存那次 562 + 4028 = 4590，热缓存那次 4540，两个数差不多，说明物理读是另算的，没有摊进逻辑读里。

我又拿一张 100 行的小表验了一遍，结论一样：

执行逻辑读物理读解释
冷缓存第一次491数据页要从磁盘读 1 次，字典等基础开销 49
第二次10页在内存里了，只摸了那 1 个页

这张表真正说明的是「第一次执行更贵」，不是「逻辑读含不含物理读」：小表总共 1 个数据页，冷缓存那次的 49 里绝大多数不是数据页，是这个会话第一次执行的解析和字典开销，第二次就只剩 0。

要判「包含不包含」，看上面那张大表就够了：冷缓存那次逻辑读 562、物理读 4028，逻辑读比物理读还小。要是逻辑读包含物理读，这个关系根本不可能出现。

所以看达梦的执行统计，两个数要一起看：logical reads + physical reads 大约是这次执行真实访问的页数。物理读高只说明缓存冷，说明不了这条 SQL 写得烂；逻辑读高才是真要改。

两个入口的数字对不上，别跨着比

同一句 SQL、同一时刻，我在 disql 里看到逻辑读 904，转头查 V$SQL_HISTORY，同一句是 772。差 15%，不是抄错。

统计口径不同：命令行的 Statistics 是客户端在会话上抓的，把解析、准备、执行整段都算进去了；历史视图记的是服务端执行那一段。具体差在哪几个阶段，我没有逐项拆开验证，但「数不一致」这件事本身就够用了：做前后对比时，从哪拿的数就一路从那拿，别改前看 AUTOTRACE、改后查历史视图。

另外 V$SQL_HISTORY 里同一句 select * 记了 772，而 count(*) 版本只有 4，跟我在命令行看到的 904 和 11 是同一个方向的关系，倍数也接近。看相对变化没问题，看绝对值会踩坑。

explain 看不到逻辑读

很多人第一反应是 explain。不行，它只给计划：

explain select * from T_LR where code='CODE500';
1   #NSET2: [8, 7500, 116]
2     #PRJT2: [8, 7500, 116]; exp_num(5), is_atom(FALSE); INFO_BITS(0)
3       #BLKUP2: [8, 7500, 116]; IDX_LR_CODE(T_LR); use_clu_addr(0)
4         #SSEK2: [8, 7500, 116]; scan_type(ASC), IDX_LR_CODE(T_LR), scan_range['CODE500','CODE500'], is_global(0)

没有 Statistics 段，因为它根本没执行。逻辑读是执行出来的数，不跑就没有。

这也解释了管理工具那个下拉为什么有三项：INDEX 就是这里的性质，只看计划；TRACE 和 TRACEONLY 是真跑。

没有 DBA 权限，也能用

这点值得单独说，因为不少环境开发拿不到 SYSDBA。我建了个普通用户 DEV1，只给了 resource 角色和一张表的查询权限，然后跑同样的命令：

-- DEV1 登录后，原样可用
set autotrace traceonly;
select * from SYSDBA.T_LR where code='CODE500';

正常输出，逻辑读 925，没有报 -5504。原因是 autotrace 是 disql 客户端自己的功能，统计信息随执行结果一起回来，不额外查系统视图，所以不需要 DBA。

注意表名要带模式名（SYSDBA.T_LR），普通用户查别人的表不加模式名会报「表或视图不存在」。

一次完整的优化，长什么样

把上面这些串起来，实际干活的流程是四步：

  1. 量基线。set autotrace traceonly; 然后原样执行那条 SQL，抄下 logical reads。
  2. 改一个变量。只改一处，加索引就只加索引，改写法就只改写法。两个一起动，数字变好了也不知道是谁的功劳。
  3. 再量一次。还是 traceonly，还是同一个客户端。数字变小就成立。
  4. 换个场景再量。把参数换成另一种取值（上面实验里 CODE500 是比较均匀的值，换一个分布极端的），确认不是只对某一个值有效。

我这边的结果：全表扫 4548，建索引后回表 911，只查索引列 11。要是业务允许只查 code，那就是 400 倍的差距，而且不用动任何配置。

顺带一句：如果这条 SQL 在别处还有调用，改完记得看那条路径。索引会让「查得快」的同时让「写得慢一点」，批量插入的场景要留意。

常见问题

管理工具的下拉里只有 INDEX，没有 TRACE？

那个下拉默认显示当前选中项，点一下箭头才展开。三项分别是 INDEX、TRACE、TRACEONLY。如果点开确实只有一项，说明工具版本较老，用 disql 那条路。

traceonly 不是只看计划吗，为什么生产库要小心？

名字容易误导。traceonly 的 only 指的是「只输出统计，不输出结果集」，SQL 本身是真的执行。大表全扫、带 FOR UPDATE、调用自定义函数的语句，在生产库里跑之前先想一下。

同一句 SQL 每次逻辑读都不一样，正常吗？

小幅波动正常。我这边连续跑同一条，出现过 904、911、925，差 2% 左右；刚建完索引的第一次是 963。换个环境波动会大些，一两成也见过。看的是量级变化（几百变几千、五千变十），不是个位数。

逻辑读和物理读，哪个更该管？

逻辑读。物理读高多半是缓存冷，多跑几次自己就降了。逻辑读高说明真的访问了那么多页，只有改索引或改写法才能降。

能不能看整个会话一共花了多少逻辑读？

这个我没实测，不写。日常判断单条 SQL 用上面三个入口就够了。

这个数多少算慢？

没有通用阈值，取决于你的表有多大、业务能忍多久。唯一靠谱的比较是跟自己的历史比：同一条 SQL 昨天的逻辑读和今天的比，同一张表加索引前后比。

最后

逻辑读这个东西的价值不在于「看懂」，在于它让你有一个不依赖别人、不依赖机器的判断依据。一台测试机、一个 30 万行的表、两行命令，十分钟就能自己把结论跑出来，不用等 DBA 排期，也不用猜。

当然它只回答「这条 SQL 干了多少活」，不回答「这个活该不该干」。业务上这个查询有没有必要存在、返回的字段是不是全都用得上，那是另一件事，数字帮不了你。

想连着排查流程一起看：达梦慢查询：一条命令把现场拍清楚，那篇讲怎么把逻辑读、执行计划、表规模一次凑齐。

卡在某一步了？

先看上面三个入口哪个最接近你的环境。还对不上，把这三样发我：卡在第几步、报错原文、select page from v$database 的结果。不用发库里的数据。
