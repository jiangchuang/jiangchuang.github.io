# 换机器清单（8 步，顺序即正确性）

> 这份清单的目标：**ECS 到期涨价 / 要换机型时，能在一个维护窗口内搬完，不丢数据、不长时间中断。**
> 顺序不能乱，尤其是 DNS 和证书这两步——搞反了就是「签不出证书，还消耗了 Let's Encrypt 的速率限制」。

## 前提判断（动手前先确认，别先做后补）

**同接入商换产品线**（阿里云 ECS → 轻量应用服务器 / 降配 / 多年付）**通常不需要重新接入备案**，
因为备案记录的是**接入商主体**，不是具体 IP 或机型。
**跨厂商**（阿里云 → 其他云）才需要办「新增接入」，一般 1-2 周，期间可能影响访问。

> ⚠️ 这一条**以你阿里云备案控制台的提示或工单回复为准**。规则会变，别拿本文当准绳。
> 要在控制台确认的问题：换机型后，备案信息里的「服务器 IP / 接入方式」是否需要变更。

## 消耗品清单（换机前先摸清）

| 东西 | 在哪 | 换机后要做什么 |
|---|---|---|
| 静态站 47MB | `/var/www/blog` | 重新 `deploy-site.sh` |
| 账本数据 | `/opt/budget/{data.json,secret.txt,img/}` | `restore-budget.sh` |
| 账本程序 | `/opt/budget/app.py` + systemd + nginx 片段 | 从 `projects/budget/` 重新部署 |
| 证书 | `/etc/nginx/ssl/` + `/root/.acme.sh/` | `cert-issue.sh --mode copy` |
| 定时任务 | acme 续期 + 每日备份 | `rebuild-server.sh` 之后手工补 crontab |
| 备案号 | 页面页脚（已在仓库里） | 无需改 |

## 八步

| 步 | 做什么 | 谁做 | 为什么必须是这个顺序 |
|---|---|---|---|
| **0** | 确认目标仍是**阿里云同账号**，并在备案控制台确认是否需变更接入 | **你（控制台）** | 跨厂商要 1-2 周，这是整个方案的前提。先动手后确认 = 白干 |
| **1** | 提前 24-48h 把 `@` 和 `www` 的 DNS **TTL 调到 600**（先记下原值） | **你（控制台）** | TTL 没降就切，回滚要等几小时。最容易被跳过、代价最大的一步 |
| **2** | 开新机，记下公网 IP，**安全组放行 80/443** | **你（控制台）** | 安全组没开，后面所有 curl 都超时，会被误判成服务问题 |
| **3** | 新机上 `rebuild-server.sh --minimal`（只落最小 :80） | 自动 | 先能应答 ACME challenge，再谈站点。反过来就是自锁 |
| **4** | `deploy-site.sh --to new --apply`，用 `curl -H 'Host: www.jiangchuang.top' http://新IP/` 验证 | 自动 | 此时 DNS 还没切，靠 Host 头验证，线上不受影响 |
| **5** | 证书：`OLD_SERVER=root@旧IP cert-issue.sh --mode copy`（在新机上跑） | 自动 | 拷证书零风险；重签要等 DNS 生效，且消耗速率限制 |
| **6** | `restore-budget.sh --from <最新包> --apply` → `verify.sh` | 自动 | 数据先落地并验收，再切流量。避免「切了才发现没数据」 |
| **7** | 切 DNS：`@` 与 `www` 的 A 记录改成新 IP，`dig +short www.jiangchuang.top @8.8.8.8` 轮询到新 IP 为止 | **你（控制台）** | 唯一没法自动的一步（没有 DNS API 凭据） |
| **8** | 观察 24h（access log、`journalctl -u budget`、`/budget/api/health`）→ 旧机**保留 7 天只读不关机** → 再退订 | 你 + 自动 | 旧机是唯一回滚路径。TTL=600 时回滚只要 10 分钟 |

## 回滚（切完发现问题）

1. DNS 改回旧 IP（TTL 600，10 分钟内生效）
2. 旧机的服务一直没关，改回来即可对外
3. 账本数据：如果新机上已经写了数据，先在新机跑 `backup-budget.sh` 取出最新包，再回旧机恢复——别直接覆盖

## 三个别踩的坑

- **别在 2026-12-29 那天做迁移**（证书续期日）。要么提前完成，要么确认新机的续期链路已经跑通（`cert-issue.sh --mode check`）。
- **别在同一天做「迁移 + 降配」**。两个变量同时动，出问题无法归因。
- **别用 standalone 模式签证书**。那要 `systemctl stop nginx`，站点直接不可用；webroot 模式不用停。

## 换完的验收

```bash
./infra/verify.sh          # 静态站 + 应用 + 证书 + 备份 + 磁盘，全绿才算完
./infra/check-site.py      # 内容一致性（目录、索引、脱敏、备案号）
```

## 关于成本（不写具体金额，价格自己查）

决定性因素只有三个，按真实影响排序：

| 因素 | 现状 | 是不是真约束 |
|---|---|---|
| **备案与接入商** | 绑定阿里云 | **是**。跨厂商 = 1-2 周 + 可能中断。这是最难用技术绕开的 |
| **有状态** | 账本要跑 Python + 落文件 | **是**。决定了不能上纯静态托管（OSS/Pages） |
| **带宽/流量** | 访问量极小（日志百来行） | **现在不是**。真涨起来再说，第一嫌疑是视频 |
| CPU / 内存 / 磁盘 | 2C/1.7G/40G 用 51% | **不是**。先做日志上限（200M）比升配划算 |

结论：**换机型（同厂商）是成本最低的路径**，工程上只需要「一条命令发布 + 一条命令恢复数据 + 一份清单」。
真到带宽成为瓶颈时，再把视频搬到对象存储——那时才需要考虑 CDN 和 301 规则能不能保留 query。
